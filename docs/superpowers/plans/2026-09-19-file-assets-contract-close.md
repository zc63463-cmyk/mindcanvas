# MindCanvas 文件与图库：契约补正及 P0-0 实施计划编制

> **执行方式：**本轮执行下列文档任务；可使用 superpowers:executing-plans 按步骤完成。这里不授权产品实现、不要求启动子代理。后续实现需独立接收评审后的 P0-0 计划。

**Goal:** 关闭现有设计中的数据正确性缺口，交付无歧义契约、可反证案例及可以独立执行的 P0-0 实施计划。

**Architecture:** 保留方案 B 的渐进方向和现有序列化格式。先定义工作区身份、操作互斥、资产持久化和迁移的边界，再将最小可用基础与后续业务实现分开；不以空实现代替完成。

**Tech Stack:** 现有 TypeScript / React / pnpm / Vitest；浏览器文件接口、IndexedDB、localStorage。本轮只读源码、修改设计文档。

**Spec:** `docs/specs/2026-09-19-file-assets-design/`；本计划针对其中需补正的契约，不能把旧的矛盾表述直接当实现依据。

## 一、范围与用户决定

- 自由画布首期不纳入工作区与文件面板；不能把这一决定延伸成用户批准了自由画布“仅会话插图”的实施方案。
- “最近”保留一个入口。当前设计选用打开时间排序；旧条目缺少真实打开时间时不得将 mtime 伪装成打开记录。
- 提供归档；在可靠移动完成后实现。归档是保留文件的应用操作，不是系统回收站。
- 引用范围未知时允许用户显式删除资产，告知影响和不可撤销边界；不允许自动清理。
- 索引层不向用户暴露；用文件位置、保存状态、来源和待重新定位等用户语言解释问题。
- 本轮允许修改七份设计文档并新增独占计划/回执，不改产品、正式测试、门禁或验收脚本，不迁移真实数据、不执行真实文件删除/改名。
- 不提交/暂存/推送/发布，不 pull/rebase/reset/stash，不覆盖旧 DELIVERY-CLOSE 证据，不启动 P0-0 实施。
- 当前成果包含未提交文件。先记录当前状态与任务文件指纹，不能只用 HEAD a2ce72b 重建工作起点；也不能把历史 808 项清单直接宣称为今天完整工作树。

### T1 关闭身份与迁移契约

**通过条件：** 至少列出同名不同目录、同目录新句柄、A→B→A、权限比较失败、旧键归属不明、新索引新增后回退六类反例及正确结果。

### T2 关闭资产写入、解析与同名契约

**读：** `packages/react/src/chrome/assetHost.ts`、`idbAssetHost.ts`、`workspaceAssetHost.ts`、`AssetPanel.tsx`；资产解析与渲染调用点。

**改：** `shared-contracts.md`、`asset-library.md`、对应验收和拆包。

- [ ] 删除 `persisted` 可代表“换机器还在”的承诺。磁盘写入成功、浏览器本地持久化、临时会话可用和可携带性分开；IDB 仍可能被清理，单文件不自动携带外部资产。
- [ ] `size + lastModified` 仅作预筛选，不可据此跳过上传。只有实际字节/可靠内容摘要核对可判定相同，否则保留冲突三选；“暂不做去重”是允许且优先考虑的最小方案。
- [ ] 写出“同名、同大小、同时间戳、不同字节”案例，正确结果必须保住用户新内容且不静默替换旧内容。
- [ ] 为上传捕获 scope/epoch/目标身份；切换后丢弃 UI 回填不等于撤销已经发生的磁盘写入。约定写入已经完成时如何记录与再次发现资产。
- [ ] 验证内存 AssetKey 与旧序列化引用的连接：浏览器素材与当前工作区素材都叫 `assets/a.png` 时，插入、保存、重开如何仍解析到所选资产？不得只在面板卡片上加 scope 后就声称问题解决。
- [ ] 选择可落地的兼容策略，例如插入前复制到当前文档可解析作用域并分配无冲突引用；无法持久绑定的场景明确限制。不能凭空恢复文档中未记录的 scope，也不自动扩展文档语法。

**通过条件：** 持久化文案与实际存储相符，同名识别不会漏上传，切换与重开不会因丢失作用域而选错图片；限制清楚写入验收。

### T3 关闭改名/移动与保存的并发契约

**读：** `apps/canvas/src/hooks/useDocumentSaveSession.ts`、`useAutoSave.ts`、`useDocumentActions.ts`、`useUnsavedTransition.ts`、`documentLifecycle.ts`、`MindmapStage.tsx`；`packages/react/src/edit/directoryHost.ts`。

**源码事实：** 当前 `suppressPendingAuto` 清除一个定时器；内容变化能重新排定。`waitForIdle` 等当前会话，不能证明所有失效会话的物理 I/O 已结束。

- [ ] 给出操作锁/租约的归属和取得时机：防止“等待空闲→新保存进入→复制删源”这一竞态。锁要覆盖自动保存、手动保存、另存为、重复操作和目标切换。
- [ ] 明确锁期间是否暂缓编辑，或保留编辑但延迟写出；给推荐并写出完整时序。草稿/IME 提交、保存失败、downloaded、内容又变、切换会话各有结果。
- [ ] 每个 await 后检查请求、文档、scope 和操作代次；`finally` 释放只能作用于自己拥有的锁，不能解开新请求。
- [ ] 明确当前文件受旧会话物理 I/O 影响时如何等待或拒绝移动。不能把逻辑 stale 当作已撤销物理写入。
- [ ] 保留内容/会话匹配才清脏、写盘事实与元数据警告分开的规则。避免新增 `rebindDestination` 与旧 `setDestination` 产生两个独立事实源。
- [ ] 明确复制成功删源失败后的当前目的地。撤销副本前若副本已被继续编辑或写入，必须保护新内容；重试删源前复查源是否外部变化，不能无条件删除。
- [ ] 不将“dirty 时改名必然丢内存内容”作为已经复现的事实；将潜在时序与正式复现条件分开。

**通过条件：** 时序表至少覆盖慢写后新编辑、锁内 Ctrl+S、锁内另存为、切文档迟到回调、部分成功后继续编辑再撤销副本、源被外部修改六类场景。

## 三、主控复核重点

1. 任意写入、复制、删除操作能回答目标是谁、写的哪个快照、失败后留下什么、谁可继续编辑。
2. 任意身份恢复能说明证据，不依赖同名/对象引用/当前目录唯一命中推断归属。
3. 文档重开时实际可重建资产绑定，不能靠上一会话内存中的 AssetKey 掩盖引用缺失。
4. 迁移回退保住升级后新增数据；“旧键还在”不是全部数据可恢复的证明。
5. 下一包有真实消费者、可运行行为测试和明确出口，没有空实现或更改正确断言来通过验收。
