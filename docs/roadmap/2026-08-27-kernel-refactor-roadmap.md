# 纯思维导图内核重构 · 开发路线图（Kernel Refactor Roadmap）

| 项 | 值 |
|---|---|
| 日期 | 2026-08-27 |
| 地位 | 内核主线开题文档（R12 总路线 ① 的执行计划） |
| 上游依据 | 联动 spec R1-R14（`docs/specs/2026-08-27-mindmap-forgejo-sync-design.md`，验收标尺）+ 调研两辑（`docs/research/`） |
| 总原则 | **移植而非重写**：成熟资产（协议层/326 测试/布局引擎）按阶段搬运，债务（44KB MapView 等）重写；每阶段带验收门禁 |

---

## 路线总览

```
K0 地基(0.5-1天) → K1 协议内核(1-2天) → K2 headless树+布局(2-3天)
→ K3 渲染层(2-3天) → K4 编辑器+插件运行时(2-3天) → K5 镜子验收+定型(1天)
                                              ↓
                              forgejo-bridge 插件立项（回到联动 spec 实施）
```

时间盒按你的压缩节奏标定（每阶段实际可并行/穿插你的功能探索）。

## K0 · 地基：新仓库脚手架与接口先行（0.5-1 天）

**做什么**：
- **新建项目 + 新仓库**：pnpm workspace 三包结构——`packages/kernel`（headless）/ `packages/react`（渲染器）/ `apps/canvas`（组合入口）；**knowledge-canvas 旧仓库降级为只读参考源**（协议层/测试/布局引擎的移植出处）
- **六注册表 TypeScript 接口定义先行**（kind / note 键 / 渲染器 / 布局 / SemRole-action / 通道）——只定义不实现
- Entity 三件套接口钉死（EntityRef / Entity / resolver，参照 knowledge-canvas `src/protocol/types.ts`）
- `docs/mirrors/` 挂三面镜子（从旧仓库复制：联动 spec、MindFlow 标注设计、PomodoroXI 接入设想）+ 本路线图随迁
- 决策文档开篇：平台选型（R14 Web-first + 库优先）为第一条 ADR；新仓库演进为第二条

**验收门禁**：接口编译通过 + 空注册表可运行的最小 kernel 骨架（一个空树 parse→serialize round-trip）

## K1 · 协议内核移植与铁律固化（1-2 天）

**做什么**：
- `src/protocol`（parser / serializer / types / uri）+ 协议相关测试**整体移植**进 `packages/kernel`
- 透传铁律测试固化：未知 kind / 未知 note 键 round-trip（W-UNKNOWN-KIND 行为）
- golden cases 随迁

**验收门禁**：协议测试全绿 + golden 全过；旧 `.mm.md` 文件新内核解析结果与旧内核一致（抽样 diff）

## K2 · headless 树与布局引擎（2-3 天）

**做什么**：
- `treeOps` / `history` 移植并**纯函数化 + 可重放操作形态**（为将来 CRDT/Loro 多设备同步留缝，零成本纪律）
- 布局引擎移植 + 渐近行为校验（对照 van der Ploeg 2013 论文，确认变尺寸节点线性时间）
- Node 环境冒烟测试（kernel 无渲染可跑）

**验收门禁**：500+ 节点布局基准测试达到/优于现值；`npm test` 在纯 Node 环境全绿

## K3 · 渲染层重写与新视觉风格（2-3 天）

**做什么**：
- **设计令牌先行**（用户对现风格不满意 → 渲染层重写即风格重塑时机）：色彩 / 字级 / 间距 / 节点形状 / 连线语言成体系定义（design tokens），作为 `packages/react` 的主题层——先定风格方向再写组件
- MapView **重写**（吸取 44KB 教训：按职责拆分——渲染 / 交互 / 小地图各自独立模块）
- 视口裁剪 + LOD + **dirty-flag 按需渲染**（禁永续 rAF，第二辑调研结论）
- 状态层选型落地：Signals + Record Store 形态（自研轻量或引入）
- 性能埋点迁移（kcPerf 四段 mark）

**验收门禁**：500+ 节点流畅交互；空闲 CPU ≈ 0（无永续 tick）；性能基线数据落档；**新视觉风格过用户审美验收**

## K4 · 编辑器完整体验 + 插件运行时（2-3 天）

**做什么**：
- 编辑交互全套移植：折叠 / 快捷键 / 大纲联动 / 富文本感知搜索 / beforeunload 守卫
- **Plugin 基类 + 生命周期自注销**（Obsidian 模式：注册即挂 unload 清理）
- 六注册表实装（允许空实现——纯内核三规则 ②）
- `apps/canvas = kernel + []` 组合入口；产出「纯文本版」构建

**验收门禁**：纯文本版功能对齐现有 knowledge-canvas 日常使用面；**无插件配置下全部测试绿**（渐进增强测试层要求）

## K5 · 镜子验收与内核定型（1 天）

**做什么**：
- 三面镜子逐一压力测试六注册表：每个镜子列「该消费者需要什么」，接口不够**先修接口**（吃狗粮条款）
- 接口冻结 v1.0，写定型 ADR
- 触发下一程：forgejo-bridge 插件立项（回到联动 spec §11 实施）

**验收门禁**：三镜子验收清单全过；`packages/kernel` 依赖图检查（零 react / 零实体解析 import——纯内核三规则 ①③）

## 启动方式（回答「怎么发指令」）

1. **本文件即开工令**：新建项目 + 新仓库，第一个 Issue = K0（脚手架），引用本文档（K0 时路线图与镜子文档随迁新仓库）
2. **每阶段节奏**：`writing-plans 出实施计划 → AI 执行工程 → 验收门禁 → 下一阶段`——门禁不绿不进段
3. **分工边界**：AI 打工程基础（脚手架/移植/测试/性能），你主导深水区（使用体验设计、功能探索、交互打磨）——K3/K4 期间你的探索结论随时插队，路线图阶段是骨架不是牢笼
4. **纪律随行**：需求先开 Issue；每个 Phase 的产出提交 git；透传铁律任何时候不许破

## 风险与对策

| 风险 | 对策 |
|---|---|
| 跨仓库移植成本（路径/依赖修正） | K1 移植时协议层与测试**目录级整体拷贝**再修 import——不做逐文件挑选；knowledge-canvas 保持只读参考态 |
| 双仓库双线并行负担 | K0 启动即冻结 knowledge-canvas 功能新增（只修 bug）；新仓库 K4 对齐验收后旧仓库归档（README 标注继任者） |
| 接口先行过度设计 | 接口只定义镜子已证明需要的 + 少量明显项；K5 才冻结，K0-K4 之间允许修订 |
| MapView 重写丢功能 | 重写前从参考源出「现有交互清单」作为 K4 验收对照表 |
| 新视觉风格反复 | 设计令牌先行且独立评审（先定方向再写组件）；风格迭代只动 tokens 层不动组件逻辑 |
| 你的功能探索改变架构假设 | 探索结论随时记入 mirrors/，属正常输入而非返工 |
