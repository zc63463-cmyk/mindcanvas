## 1. 类型设置

### 1.1 意图解读(请校对)

原稿结构:

```
## 类型设置
<!-- desc: 属性类型 , 颜色类型, 标注形状类型 -->
### 节点类型设置
### 新节点
<!-- desc: 可做二层分类,用途-类型;note: 1. 项目 : 设计, 目标, 功能, 问题 -->
### 注释类型设置
#### problem / #### 目标 / #### 设计 / #### etc.
```

我的读法(推测,请校正):

- 想要的是一套**类型注册表**:每个类型带三类东西——**属性**(数据)、**颜色**(视觉)、**标注形状**(视觉);
- 两个应用域:**节点**与**注释**(note);且两域共享词汇(「设计/目标」两侧都出现)→ 可能是**一张表、两个使用面**;
- 节点类型支持**二层**:**用途 → 类型**(示例:项目 → 设计/目标/功能/问题)。

三处必须校对:

1. 「属性类型」是否指"类型可带自定义字段"(如 problem 类型自带 severity/状态)?还是仅指类型的分类维度?
2. 「标注形状」指**节点盒形状**(椭圆/云形等),还是**标注标记的形状**(角标/框/圈)?两者成本差一个量级(见 D3)。
3. 「新节点」一节,是否指"新建节点时的类型/用途选择流程"?

### 1.2 现状零件(可复用的先例)

| 零件 | 位置 | 可复用点 |
|---|---|---|
| 实体 kind 语义色 | `KIND_META`(packages/kernel/src/protocol/types.ts:289-299) | 「类型→颜色」已有先例,且是**覆盖分支色**的方式 |
| Section 色板 | `SECTION_COLORS` 六色 + `SECTION_PALETTE`(packages/react/src/render/sectionFrames.ts:31-38) | 「token 落盘、未知值透传、渲染回退」的颜色纪律 |
| note 未知键透传 | `Note` 索引签名(packages/kernel/src/protocol/types.ts:39-133) | 新增 `type` 键 **parser/serializer 零改动** |

缺口:

- **节点级形状渲染不存在**:NodeG 统一 `<rect rx>`(packages/react/src/render/NodeG.tsx:154-165)——形状要动渲染+布局+命中+导出,成本最高;
- **节点级颜色没有用户通道**:只能通过 kind 语义色覆盖,没有「节点自定义色」。

### 1.3 设计空间(四个决策点)

**D1 类型注册表放哪?**

| 方案 | 优点 | 代价 |
|---|---|---|
| A 全局(设置面板/localStorage,不进文件) | 轻、零协议改动 | 换机/清缓存即丢;外部 Agent 读文件时不知道类型语义 |
| B 文档级(根 note `types:` 键) | 纯文本事实源完整、AI 可读、sections 同款先例 | 每文档重复定义;需新访问器 + roundtrip 锁死 |
| C 混合(定义全局、使用落盘) | 折衷 | 两处真理,同步心智负担 |

**推荐:两步走**——
① **词表先内置**(3–6 个类型硬编码),把「打标 → 视觉 → 写回 → roundtrip」全链路跑通;
② 全链路成立后,自定义注册表落**文档级 `types:`**(sections 同款:根 note 元数据 + 访问器 + 零数据面改动),由「类型设置」面板编辑它。
理由:自用摩擦驱动,先证明打标循环有用,再建注册表管理 UI;目标形态保持纯文本事实源纪律。

**D2 二层分类怎么表达?**

| 方案 | 形态 | 适合 |
|---|---|---|
| A 双键 | `use: 项目` + `type: 设计` | 视觉分层(用途→色系、类型→深浅/形状) |
| B 复合单键 | `type: 项目/设计` | 检索/统计/语义;最便宜 |
| C 注册表树 | 定义里组织父子,节点只存叶子 | 类型体系稳定后 |

先回答「二层为谁服务」:视觉分层?筛选统计?给 AI/自己的语义?——答案决定选型。**若暂时说不清:B 起步**(一字符串,后续可无痛拆分)。

**D3 视觉编码通道分配(本方向真正的难点)**

| 通道 | 现状占用 | 可用性 |
|---|---|---|
| 填充/边框色 | 分支色板(结构)、kind 语义色、Section 色 | **已拥挤**:类型色进入必须先定义优先级 |
| 边框样式(虚线/粗细) | 空闲(选中态为临时态) | 干净的语义通道 |
| 角标/图标 | center 角标、note 角标、LOD 角标 | 未饱和,成本最低 |
| 节点形状 | 无(主题 shape 仅圆角差异) | **成本最高**(渲染+布局+命中+导出) |

推荐:**v1 = 角标 + 边框样式/浅底色**;**形状后置**,或只做「标记形状」(角标形状,不动节点盒)。同时**先写下优先级规则**(例:选中态 > kind > 类型 > 分支色),否则叠加时行为不可预期。

**D4 注释类型落在哪一级?**

| 落点 | 说明 | 成本 |
|---|---|---|
| 条目级(每条 note 带类型) | `note[]` 从 string 升为对象;动协议形态 + 兼容读取 + roundtrip | 中 |
| 块级(整个 note 一个类型) | 加一个 `note_kind` 键;渲染整块着色 | 低 |
| 只作渲染样式 | 类型仅影响卡内视觉(色条/标记) | 低 |

提示:注释类型(problem/目标/设计)与节点类型共享词汇,建议**同表两用**;落地点 v1 建议**块级或只读展示**,条目级与编辑入口后置。

**打标入口**(与既有体系一致):右键菜单 + 二级环席位;类型管理入口放设置面板(后置)。

### 1.4 风险与非目标

- **体系膨胀**:「属性类型」(自定义字段)是重头——v1 明确列为**非目标**(它是"元数据编辑器",价值后置);
- **视觉过载**:颜色通道已有三条占用;类型色要克制(建议与 Section 同源色板,6±2 色);
- **协议成本可控**:走 note 透传 = 零 parser/serializer 改动,但需 roundtrip 锁死 + canonical 用例(纪律)。

### 1.5 规模

| 范围 | 规模 |
|---|---|
| v1(打标 + 角标/边框 + 色,不含形状/属性/条目级) | **M**(3-6 天级) |
| 完整版(形状 + 属性 + 二层) | **XL**,建议后置/再议 |

**成功判据(自用)**:不看笔记,仅凭视觉能区分「问题/目标/设计」节点;且画布没有变花。

### 2.2 设计与决策

**D1 duplicate 接线(先做,最便宜)**

- 入口:右键菜单「创建副本」(注意 v1.8.2 菜单首屏 12 行预算)+ 可选 Ctrl/Cmd+D;
- ⚠️ **cid 债务(本次实测)**:`cloneSubtree` 浅拷贝 `note`(treeOps.ts:316)→ **cid 被原样带走** → 与源子树重复 → 读侧 `dup-cid` 诊断(协议 §6.3)+ centers/sections 锚歧义。接线时必须在命令层处理:**复制出的子树清 cid**(符合"复制即独立"的既有语义);要独立岛可再升格。

**D2 复制子树 Markdown(给 AI / 跨文档的读通道)**

- 主体:**canonical 化子树**——标题链(≤H6)→ 混合子节点降列表,2 空格缩进(协议 §七 规则);
- 元数据:**含 note 块**(desc/note/note_text 是语义);**剥离 cid**(跨文档无意义 + 防 dup-cid)与纯视觉键(lens/len/beamAt 等,AI 契约 §1.1 同口径);
- 变体(可选后置):「纯文本版」(只有结构、无 note 块);
- 落点:kernel 新增「子树片段序列化」函数;ADR-0004 冻结不妨碍**新增**导出,走正常流程。

**D3 粘贴回画布(闭环另一半,可二期)**

- 最小版:粘贴文本 → 尝试按 mm.md 子集 parse(保守判定,失败忽略)→ 挂为选中节点子级 → cid 重分配(维护 `next_cid`);
- 边界:剥离文档级块(centers/edges/sections);与「普通文本粘贴」互不干扰;
- 价值:AI 产出片段可一键进画布——把协作从「文件级」细化到「片段级」。

## 3. 摘要型节点

### 3.1 两种解读(先拍板)

- **A. 内容型节点**:一类节点,盒内渲染一段富文本(段落级 markdown 子集);「摘要」= 概括性正文;
- **B. desc 升级**:不做新类型,把现有 desc(盒内、纯文本、软上限 16 行)升级为富文本渲染;
- (C. XMind 式「分组概括」——按草稿措辞可能性低;若是本意请纠正。)

下面按 A 讨论;3.3 的第 1 档对 B 同样成立。

### 3.2 现状:一个被卡住的半成品

- **行内 tokenizer 已有、渲染层未消费**:`tokenizeInline` 支持 `**加粗**` / `` `code` `` / `[label](url)`(packages/kernel/src/layout/inline.ts:1-64),测量已接(nodeLayout.ts:98-99),**但 NodeG 只画纯文本**(packages/react/src/render/NodeG.tsx:275-287)——"tokens 无消费方";
- 块级渲染能力只在卡背:`CardBackMarkdown`(标题/列表/引用/代码/表格;packages/react/src/chrome/CardBackMarkdown.tsx);
- desc 现状:盒内、纯文本、行高 15、软上限 16 行、**占布局**(DescBlock.tsx;createDescMeasure,packages/react/src/demo/pipeline.ts:155-173)。

### 3.3 三档推进(由轻到重)

1. **行内富文本落地(消费 tokenizer)**——标题/desc 的 `**加粗**`/`code`/链接真正渲染(tspan)。
   规模 **S~M**;收益/成本比最高(现成缺口)。注意:NodeG.memo 与 pan 性能(动渲染先跑 mapview-pan-memo.test);链接点击命中需 stopPropagation(参考 L 批次经验)。
2. **desc 富文本化 + 行数放开**——B 路线的全部 / A 路线的中间档。**S~M**。
3. **内容型节点(块级)**——节点盒内段落级渲染,技术分歧:
   - (i) tspan 扁平化:稳、导出友好,表达力有限;
   - (ii) foreignObject:表达力强,导出/命中/性能风险(Canvas 后端有兼容问题);
   - (iii) HTML 覆盖层:项目已有先例——note 浮窗就是 HTML 定位在节点上;
   - **L~XL,建议单独立项**;且必须先回答 3.4 的定位问题,否则与 note 卡功能重合。

### 3.4 定位问题(回答后才能开工)

「摘要型节点」与「节点下方常驻 note 卡」功能高度重叠(都让节点旁出现成段内容)。差别在**归属**:

- 内容属于**节点本体**(随节点缩放/被布局当节点/导出包含)→ 走"内容型节点";
- 内容属于**附着物**(可关、独立槽位、有 presence 提示)→ 那是 note 卡的地盘。

**裁决问题:你要的是「节点本体承载内容」,还是「节点旁的附属内容」?**

## 4. 笔记模式 : modal

### 4.1 现状(准确口径)

- NotePopover 双模式:**floating**(屏幕浮窗;悬停预览与**编辑态**都走它)/ **embedded**(世界空间**卡片**,节点下方固定槽,随画布缩放;NotePopover.tsx:299-348);
- 「卡片形式」= embedded 固定卡:**GAP 12 + 卡高 120 = 132px,由布局 measure 计入**(NoteGrowthPanel.tsx:13-25;pipeline.ts:195、236)——**它确实占布局**(项目口径:"固定 note 笔记在节点下方向下生长并参与布局",contextMenuItems.ts:8-9);
- 卡内结构:头部(点击固定 / ⟳翻面 / ✕)+ 序列区(note)+ 正文区(note_text);翻面(嵌卡 + md 非空)看 note.md——**P1/P2 刚完成,背面可编辑**(NoteBackEditor);
- LOD:k≥0.65 整卡;0.35–0.65 角标;<0.35 剔除(fixedNotePanels.ts:14-32)。

### 4.2 终态裁决:卡片与翻卡的去留(本方向的核心问题)

- 翻卡 = **卡片范式内**的深度阅读(在 120px 槽里看全文,本就是妥协);modal = **跳出卡片范式**;
- 两个问题:**①卡片形态保留吗?②翻卡保留吗?**
- 产品倾向(请裁决):**卡片退为「提示层」**——角标/小条承担"这里有笔记"的可见性;**md 阅读/编辑迁 modal**;**翻卡可退役**——P2 的背面编辑成果**迁入 modal**(能力不废弃,只换宿主);
- ⚠️ 卡片槽是布局的一部分:动它 → 森林重排(参考 F 批次「note 预留移除 → 重排过渡窗口 ~40px 级」经验,过渡期用 waitForStablePos 类方法验收);
- 备选:并存(卡片 + modal 双通道)——成本低、无破坏,但两个阅读入口长期会分叉维护。

### 4.3 若做 modal 的设计要点

- 复用:`CardBackMarkdown`(md 渲染)、`NoteBackEditor`(md 编辑)、`NoteBody` 三态逻辑、统一提交链(防双 undo 纪律);
- **新组件**(建议 `ModalNoteView`,**不扩 NotePopover**——600/600 零余量是硬线);
- 遮罩先例:锚点选择器已用 portal + fixed 遮罩(NotePopover.tsx:569-576);
- 交互:Esc / 遮罩点击关闭;焦点守卫(浮窗编辑态先例);**模式粒度**建议先做全局显示偏好(不落盘),稳定后再议文档级;
- 编辑走既有 `onChangeNote` / `onChangeMd` 链;LOD/缩放无关(屏幕空间)。

### 4.4 规模

| 项 | 规模 |
|---|---|
| 一期(modal 读写,卡片并存) | **M**(3-5 天级) |
| 二期(卡片槽瘦身/布局重排) | 单独评 |

**成功判据**:长笔记读写不再受卡片尺寸约束(不受 k 缩放影响)。

## 5. 横向纪律(四组全适用)

- **落盘键走 note 透传**:零 parser/serializer 改动模式 = 类型定义 → 独立访问器(protocol/xxx.ts)→ 消费(渲染/菜单)→ controller.updateNote 写回;frame/section 是先例;
