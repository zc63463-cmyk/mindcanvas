## 1. 判据（逐条对应复核回执 §5，均经我实读确认）

### 1.1 删除的动机不成立——增长循环已证伪

复核以受控夹具证伪「两库互相喂大」：

- `QUAL-C`（决定性证据）：旧库已含 `v1`/`v2` 两行、**不做任何 `registerDoc`**，
  纯跑 `migrate()` → `{"migrated":0,"unchanged":2,"failed":0,"historyPool":0}`，
  旧库 ids 完全不变。每一行都被 `legacyKeys` 认出「已被索引认领」，不会被当新文档读成新条目。
- 稳态实测：路径稳定时 30 个会话 `lib=1, idx=1` 全程恒定，**每会话净增 0 行**。

即：不存在「无界互相喂大」。删旧键**不是为了终止任何增长**——这一动机不能作为 DS-10 的决策依据。

### 1.2 旧键不删是当前三条不变量的依赖

1. `projectLibrary` 的并集语义（`docIndexProject.ts:86-92`）依赖旧库孤儿行不被抹掉
   → 契约 §6.2.1「用户不处理也不丢」。
2. `projectStarred` 的 `claimedByIndex`（`:114-139`）依赖尚未迁移的旧键仍在旧集合里
   → 否则「投影反过来删掉迁移的输入」（注释 `:128-131` 自陈实测踩过）。
3. 损坏旧键须留存才能「下次重试」（NC-1 路径；N-2 修复后 `:236` 已断言 `failed`）。

删旧键的时序若早于「迁移确认完成」，会**同时破坏上面三条**。

### 1.3 选项 (b) 当前不具备实施条件

「迁移完成后删已被认领且不再是任何条目当前 relPath 的旧键」需要一个**可判定的「迁移完成」信号**；
现无此信号：`cursors` 会归零重跑，`migrated/unchanged` 是每批计数，均非全局完成态。
在此信号存在之前实现 (b)，只能靠猜。

### 1.4 代价可测，且与运行时长无关

残留量 ≈ 该文档历史路径数 − 1，与**改名次数**线性相关（`ADV-3`/`ADV-4`：每次改名 +1 行、随后立即收敛），
与「运行多久 / 开多少次」无关。P0-A（改名 / 移动）落地后才有完整的「改名 → 旧键作废」视图，
届时删除判据才能被完整定义。

## 2. 附带约束（将来若改走 (b)，以下为前置条件）

1. **删除判据必须能区分「损坏未迁移」与「已认领」**（复核 §5.5）。直接以「不在 `failed` 里」
   作为「已迁移」判据会误删损坏数据。
   - 相关缺口已在本轮修复：N-1（投影侧配额失败谎报）由 `071e478` 写后回读校验闭环；
     N-2（`failed` 计数无断言）由 `037d1e2` 在 `doc-index.test.ts:236` 补断言闭环。
   - 但「删除判据显式处理 failed」这条在 (b) 实现时仍须单独设计，不得默认成立。
2. 删除实现必须配判别性负控（中性化删除判据后须有用例转红），遵循 `p0-0-implementation-plan.md` §5 纪律。
