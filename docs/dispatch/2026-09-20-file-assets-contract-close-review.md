# FILE-ASSETS-CONTRACT-CLOSE 第二轮返修复核

日期：2026-09-20。结论：R1/R2/R3 的接口方向可接受，requestPermission 已纳入接线；P0-0 实施计划仍需定向修订，暂不放行实现。本轮不重开 DELIVERY-CLOSE，不修改交付者文档或产品代码。

## 1. 已接受部分

- LegacyHandleIntent 明确写/删/不动，detach 两键同事务的目标成立。
- 注册表读取区分 ok/empty/corrupt/unavailable，禁止读失败触发 legacy adoption。
- 写接口改为事务内 mutate，不接收事务外整份快照作为常规写入方式。
- requestPermission 的未挂载路径纳入统一身份解析，已挂载时不无故变更身份与 epoch。
- 原 IDB 夹具重复 accessor/property 引起的 TS1119 已消失。本结论只是针对该诊断，不代表片段完整类型检查或行为正确。

## 2. 本轮必须修订的四项

### CR2-1：明确不同被错误归入未知，阻断第二工作区的持久登记（P1）

锚点：`p0-0-implementation-plan.md:677`、`:687`、`:724`；`shared-contracts.md` §1.2.6。

计划把全部 `different` 与 `unknown` 均送入不写任何键的 unassociated 分支。这意味着 A 登记后，正常选择可证明不同的 B 也不能登记；刷新会回到 A。A→B→A 用例只看内存 ID 不等和返回 A 的 ID，未断言 B 曾持久登记、A 曾变 dormant，能漏掉此退化。

修订规则：唯一 same → 复用；全部明确 different（以及合法空注册表）→ 登记新身份；无 same 且存在 unknown → 保守降级；多个 same → 明确拒绝合并/降级。不要把“注册表键存在但 entries=[]”等同已有身份不明。

补用例：A→B 后 B 为 disk/persisted、active=B、A=dormant、裸键=B；新实例 restore 仍为 B；再选 A 恢复 A 原 ID。保留相同名称但不同目录用例。

### CR2-2：夹具仍不能支持事务中止与原子回滚（P1）

锚点：计划 §4.2 `makeTx()`，尤其行 375–425；写入算法行 595。

主控直接提取计划里的 v2 夹具运行，得到：`abortType=undefined`、`readFailed=true`、`completed=true`、`stored=after`。也就是读取错误后仍执行后续 put 并提交；而生产计划要求错误分支调用 `tx.abort()`。夹具的 put/delete 直接修改 memStore，没有提交前暂存与失败回滚能力，不能据此证明 R1 原子性。当前 fail.write 只在整笔操作开始前失败，覆盖不到首个写请求成功、后续请求失败这一关键窗口。

修订要求：补 abort/onabort、请求失败后的中止、成功与失败互斥结算、事务内暂存、提交时发布、abort 时丢弃；或选用已安装 fake-indexeddb 并明确处理原生句柄与函数替身不可克隆的边界。不能靠生产实现绕开 abort 来迁就测试。

必须验证：两个键初始有值；第一条 put 已执行后第二条写/删除失败；最终两个键均保持旧值、Promise 收束、oncomplete 不触发。另覆盖主动 abort、mutate 抛错、记录非法、读取失败。夹具校准可独立放在交付者独占目录，不改产品代码。

### CR2-3：两条宿主测试的期望与前提不成立（P1）

锚点：计划行 747–758、782–788。

1. unassociated 用例先成功挂载 A 并写裸键，再声明不写任何键，却断言 `getDirectoryHandle()` 为 null。正确结果是原 A 句柄仍在。保存操作前后的可读目标/身份并比较，不要用 JSON.stringify 比较含函数/句柄对象来证明内容逐字未变。
2. unavailable 用例在新实例 restore 前把整个 IDB open 设置为失败，此时连旧裸句柄也无法取回，不具备挂载 disk-session 的根句柄。必须区分“picker 已返回可用句柄、注册表不可读 → 可会话挂载”和“冷启动 restore 且整个存储不可读 → 未挂载/false”。如果只想失败注册表读取，应只注入该键读取错误，让裸键仍可读。

以上是设计测试修正，不是反转已经正确的产品断言。补出 mountWithPicker/reboot/handleOf 等辅助函数及权限初始化/复位规则，保证测试可直接落地，而非依赖未定义 helper。

### CR2-4：NC-5 受同页串行链遮蔽，尚不能证明事务内合并（P1）

锚点：计划行 330、489–500、932–938。

生产设计用 writeChain 包住整个读写过程。同页 Promise.all 的两次调用因此串行；仅把读取移到事务外而保留 writeChain，仍会先完成第一次更新，再读到新值，不一定转红。主控用最小调度反例验证：事务外读但保留整段串行链，结果仍为 `[a,b,c]`。这不是产品测试，是对“该负控必然失败”的反证。

补两个独立调用方/模块实例，共用数据库但不共享 writeChain；用 barrier 控制两个事务外读取都完成后再写。正确事务内 RMW 保留两条更新，负控丢一条。不要额外删除 writeChain 才制造红灯，却仍称只中性化事务内读取。

还需明确异步 sameDirectory 比较与事务内 mutate 之间的版本/归属复核：不要把“事务内调用一个使用旧快照的闭包”当作已解决并发。若比较结果依赖的条目在提交前变更，应重试解析或拒绝；不能在 IDB 活跃事务中等待不受控外部 Promise。至少给出一个两调用方从空库同时识别同一目录的处理口径。
