## 0. 裁定方法（先说标尺，再逐项套用）

按顺序问四个问题，**前一个不成立就不必问下一个**：

1. **契约有没有承诺这项能力？**（读 ADR / 设计稿 / 验收清单，找明文）
2. **如果承诺了，交付物在不在？**（读源码 / 工具 / 测试）
3. **执行所需的现实条件，本机 / 本仓具备吗？**（浏览器、playwright、Windows、真实输入法）
4. **只有在①②都成立、③缺失时，才可能是阻断。**

由此得到三档定档，**不使用"阻断/不阻断"这种二分**，因为它们的代价不对称：

| 定档 | 含义 | 后果 |
|---|---|---|
| `release-blocker` | 已承诺的能力有缺陷，用户会踩 | 不清不能发 |
| `pre-release` | 已承诺的能力未取证，但无据显示是缺陷 | 要么补取证，要么在发布说明里明示"未验证"后发布 |
| `post-release` | 契约显式不承诺，或已闭环 | 不阻断发布，登记为后续项 |

### ⑤ mode-guard 抖动（保存中指示闪一帧）→ `post-release`（已闭环）

| 项 | 内容 |
|---|---|
| 契约怎么说的 | 承诺「blocked 时不闪 saving」，且有具体守卫 |
| 交付物在不在 | **在**。`apps/canvas/tests/mode-guard.test.tsx:326-329` 断言「导图有未保存编辑 → 进入自由画布前必须确认；取消保留编辑与画布」，在 `expect(saveState(container)).toContain('未保存')` 处守住状态语义；守卫在 saving 置位**之前**判定（`useDocumentSaveSession.submit` 的 `guard` → `blocked`，任务不入队、saving 零变化） |
| **定档** | **`post-release`** —— 契约承诺的**状态语义层面已闭环**（有守卫、有回归断言）。 |
| ⚠️ 但必须区分两层，不得混为一谈 | **状态语义**已闭环（断言守住）；**帧级时序**（是否真的一帧都不闪）属未验证的延伸——jsdom 断言不能覆盖真实帧时序。本裁定**不为帧级时序另立阻断级**，但要如实记录：**"零帧闪烁"在真实浏览器中未验证**。 |
| 另需登记的一条**已实测**的已知 flaky | `apps/canvas/tests/mode-guard.test.tsx:329` 在全量并发下**偶发**红（`expected '✓ 已保存' to contain '未保存'`），单独跑 11/11 绿、我连跑 3 次 3/3 绿。这是**测试自身的负载相关抖动**，不是产品缺陷，但它是**非确定性红**——按同一把尺子，它不能被当作可靠回归门禁（见第 3 节）。 |

## 3. 由本裁定顺带确认的两条发布判据纪律

这两条不属于五类边界，但裁定过程中实测到了，须一并写进发布清单：

### 3.1 「非确定性红即不可作回归门禁」

实测到两处墙钟/时序断言随负载自发转红：
- `apps/canvas/tests/mode-guard.test.tsx:329`（本轮实测：全量并发偶发红，单跑 3/3 绿）
- `packages/kernel/tests/benchmark-layout.test.ts:78`（独立评估实测：连跑 8 次第 7 次红）

**判据**：出现非确定性红的套件，其「全绿」不能当作可靠的发布门禁证据。**同一把尺子适用于 S5 的 106 断言矩阵** —— 这也是为什么它必须真机复跑，而不能靠静态统计 `check(` 调用次数替代。

### 3.2 证据可达性是独立于边界的一类缺口

S5/S5-R2 的全部原始证据不在 `main`（`outputs/` 计数 0），而 `CHANGELOG.md:25/73/76/82` 以「已落盘」语气引用这些路径。这**不是**五类边界之一，但它是发布前必须处置的：
- **必做**：改措辞（标注「旁支证据」）+ 停止引用在 `main` 上落空的行号。
- **条件性可选**：把证据合入 `main`。
