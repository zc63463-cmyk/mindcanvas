### 3.3 问题 2：两库互相喂大 —— 复现还是证伪？

**判定：证伪（refuted）。不是真缺陷，也不是「有界噪音」——稳态下零增长；
唯一的行数增长来自「文档真的被改了名」，且改名后立刻收敛。**

用受控夹具（同一 store 跨会话重建 `DocIndex` 模拟「关闭 → 重开」）实跑。

#### 3.3.1 四组基本场景（每会话：新建 DocIndex → registerDoc → migrate → 投影）

```
[GROWTH-A] 真实工作区（有证据），打开 1 份文档，6 会话

[GROWTH-B] 无历史证据工作区（legacy adoption 新 scope），6 会话

[GROWTH-C] 起点：旧库 1 条孤児行，6 会话

[GROWTH-D] 浏览器自由画布（relPath=null）+ M8，6 会话

```

**每会话净增 = 0 行**。索引条目数亦恒定（1）。**无上限问题——因为根本没有增长。**

#### 3.3.2 对抗场景（专找派单方假设的反馈环）

```
[ADV-1] 多文件夹同名（A/B/C 各一份「同名.mm.md」），5 会话：旧库行=3 索引=3 恒定
[ADV-2] 浏览器 relPath=null，4 会话：旧库行=0 恒定
[ADV-3] 每会话改名（文档v1→v5）：旧库行 1,2,3,4,5  索引 1,2,3,4,5  ← 有增长！
[ADV-4] 打开 3 份 + 第 5 会话改名一次，10 会话：
  旧库行 = 3,3,3,3,3,4,4,4,4,4   ← 改名当次 +1，随后 5 个会话恒定
  终态 ids = ["x-renamed.mm.md","x.mm.md","y.mm.md","孤儿.mm.md"]
```

**关键区分**：`ADV-3`/`ADV-4` 的增长**只发生在 `relPath` 真的变化时**，每次改名 +1 行，然后立即收敛。

#### 3.3.3 决定性对照：反馈环是否存在？

```
[QUAL-A] 路径稳定，跑 30 个会话
 s1:lib=1,idx=1 s2:lib=1,idx=1 ... s30:lib=1,idx=1     ← 30 会话全程恒定

[QUAL-B] 仅第 3 会话改名一次，再跑 30 会话
 旧库行数序列 = 1,1,2,2,2,2,2,2,2,2,...（第 3 会话后一直是 2）
 终态 ids = ["v2.mm.md","v1.mm.md"]；终态索引条数 = 2

[QUAL-C] 制造改名残留后，【不 registerDoc】，只跑 migrate()
 改名后旧库 ids = ["v1.mm.md","v2.mm.md"]；索引 = 2
 纯 migrate（无 register）结果 = {"migrated":0,"unchanged":2,"failed":0,"historyPool":0}
 索引 = 2；索引 docKeys = ["ws:aaaa::v1.mm.md","ws:aaaa::v2.mm.md"]
 旧库 ids = ["v1.mm.md","v2.mm.md"]     ← 完全不变
```

**`QUAL-C` 是判定反馈环的真伪的决定性证据**：在旧库已含 `v1`/`v2` 两行、且**不做任何
`registerDoc`** 的情况下重跑 `migrate()`，结果是 `migrated: 0, unchanged: 2`
—— 旧库的每一行都被 `legacyKeys` 认出「这条已被索引认领」，**不会被 M5 当新文档读成新条目**。
投影写出的相对路径 id 与索引条目的 `relPath` 同一性由 `legacyKeys` 维持，**没有正反馈**。

#### 3.3.4 结论与量级

| 问 | 答 |
|---|---|
| 是「真缺陷 / 有界噪音 / 派单方读错」？ | **派单方读错了**（第三种）。增长循环不成立。 |
| 每会话净增几行？ | **0 行**（路径稳定时）。 |
| 是否有上限？ | 不需要上限——无增长。行数 = 索引条目数 ∪ 旧库原有行（含孤儿）∪ 畸形行，**每次投影重新算，是幂等的并集**。 |
| 那 `ADV-3/4` 的增长是什么？ | **改名残留**，不是反馈环。文档每改一次名，旧库多留一条老路径行（旧键不删 = DS-10）。改名停止 → 增长立即停止。 |
| 派单方读错在哪？ | 把「投影的行集合是并集（只增不减）」等同于「两个存储互相喂大」。并集是**同一轮内的稳定语义**：索引条目按 `id` 对齐复用旧行（`docIndexProject.ts:76` `{...prev}`），不是每轮追加。派单方引用的 `:111,128`「拒绝移除尚未迁移的旧键」防的是**投影删掉迁移的输入**，与增长无关。 |

## 5. 「对 DS-10 的输入」单列一节

> **本节只提供判据，不做 DS-10 裁定（那是主控的）。**

**我的问题 2 结论对 DS-10 的约束：**

1. **增长循环不成立** → 删旧键**不是**为了终止任何「无界增长」。DS-10 **不因增长而变成必须处置**。
   派单方设想的「若不删则两库无界互相喂大」这一动机**不成立**，不能作为 DS-10 的决策依据。

2. **旧键不删的真实代价是「改名残留」**，且量级可测：
   - 路径稳定：旧库行数 = 索引条目数，**恒定**（30 会话实测 `lib=1,idx=1` 全程不变）。
   - 每改名一次：旧库/索引各 **+1 行**，**立即收敛**（改名后 28 个会话恒定在 2）。
   - 即：**残留量 ≈ 该文档历史路径数 − 1**，与「会话数」无关，与「改名次数」线性相关。
   - 因此 DS-10 的选项空间应按「**用户改过多少次名**」评估，而不是按「运行多久/开多少次」。

3. **旧键不删的收益（当前设计明确依赖它）**：
   - `projectLibrary` 的并集语义（`docIndexProject.ts:86-92`）**依赖旧库里的孤儿行不被抹掉**
     → 「用户不处理也不丢」（§6.2.1 `:881`）。
   - `projectStarred` 的 `claimedByIndex`（`:114-139`）**依赖尚未迁移的旧键仍在旧集合里**
     → 否则「投影反过来删掉迁移的输入」（注释 `:128-131` 自陈实测踩过）。
   - NC-1 若能修（`failed` 计数上抛），也要求损坏旧键**不被删除**才能「下次重试」。
   → **删旧键的时序若早于「迁移确认完成」，会同时破坏上面三条。**

4. **可判定的选项空间（供主控选）**：
   - **(a) 不删**：当前状态。代价 = 改名残留线性累积；收益 = 上述三条不变量全保。
   - **(b) 迁移完成后删「已被索引认领且不再是任何条目的当前 relPath」的旧键**：

### N-1 [medium] library 投影键配额失败被静默吞掉，`projectionFailed` 谎报 `false`

  确实「捕不到被 `save` 吞掉的配额失败」，且**实测结果为 `projectionFailed: false`**（比其自陈更严重
