### 4.3 §6.2.1 归属证据规则（本包核心守卫）

`hasOwnershipEvidence(ctx, relPath)`（`docIndexCore.ts:310-330`）是 M5–M7 的归属判据，返回 true 当且仅当：
`relPath` 非空 **且** 作用域已持久 **且** 该作用域有历史证据。
其签名只收 `(ctx, relPath)`，**无从**感知「同名命中数」或「是否已有索引条目」。

明确**不构成证据**的情形（逐条有用例）：
1. **唯一同名命中** → `唯一同名命中不自动绑定，进历史池`；
2. legacy adoption 新生成的 `scopeId` → `hasOwnershipEvidence：无 relPath / 未持久 / 无证据 一律 false`；
3. `ephemeral: true`（上次会话 disk-session）→ `ephemeral（上次会话的 disk-session）作用域的旧条目进历史池，不自动绑定`；
4. **多个同名命中 → 本包未实现专门分支，也没有独立用例**。
   更正第 1 轮的说法：M5 的认领判据**不是** `hasOwnershipEvidence`，而是
   `existing = index.docs.find(e => e.scopeId === ctx.scopeId && (e.relPath === key || e.legacyKeys.includes(...)))`
   （`docIndexMigrate.ts:104-110`）——「多个同名」由**索引主键唯一性**天然消解（同一 `scopeId` 下同一 `relPath` 只会有一条条目），
   不存在「多个同名仍可能误绑」的路径，因此也没有为它单写用例。
   `grep -n "多个同名" apps/canvas/tests/doc-index.test.ts` → 无命中。

用户显式「关联到此工作区」是**唯一合法绑定动作**，写入 `relinkEvidence: { at, via: 'user-confirmed' }`：
`用户显式「关联到此工作区」后才绑定，并留下 relinkEvidence`。

**`relink()` 的 `return true` 不含投影成败**（第 3 轮补充，第 1/2 轮未写）：
`docIndex.ts:340-343` 里 `this.commit()` 的返回值被丢弃，`return true` 是**无条件**的——
即投影写失败时 `relink()` 仍报成功。而 `relinkEvidence` 是一次写入、不可撤销
（见 §8/§R2-3，「不可撤销为假」）。因此 `relink()` 返回 `true` 只表示
「两道拒绝未命中、绑定已写进索引」，**不表示**该次绑定已可回退。
调用方要判可回退须另查 `projectionStatus().projectionFailed`（`projectionStatus` 是唯一读取面）。
同理，`mutate` / `commit` 驱动的其余写路径返回 `void`（第 3 轮把它们从 `IndexChangeResult` 收敛为 `void`），
签名本身**无法**区分「已写且可回退」与「已写但投影失败」——这是有意的：投影状态只经 `projectionStatus()` 单点暴露。
「忽略」只从呈现移除：`忽略只从呈现移除，不改索引、不删旧键`。

历史池用**用户语言**：`formatHistoryPool(n)` → `「N 条旧记录未关联工作区」`；
默认折叠，展开为列表，每条「关联到此工作区」/「忽略」（`FileManagerViews.tsx:HistoryPool`）。

## 7. P0-A 索引更新契约（下一包可消费）

P0-A 改名/移动当前文档时必须维持「当前文档、索引、真实保存目的地一致」。本包提供的可消费面：

### 7.1 稳定身份：收藏与「最近」不跟路径走

- **收藏按 `docKey` 存**（`setStarred(docKey, bool)`），`relPath` 是缓存字段。
  改名/移动后**只更新 `relPath` 与 `name`**，`starred` 与 `lineageId` **不动** → 收藏连续性由身份保证，不靠路径。
  已用例锁定：`收藏跟稳定身份走：relPath 改了收藏不丢`。
- **`docKey` 由 P0-A 负责**：工作区用 `wsDocKey(scopeId, newRelPath)`（`docIndexCore.ts:184`）。
  注意 `wsDocKey` 对 `browser:local` 会**回落** `browser::<id>`（防止 `ws:browser:local::x` 这种
  谁也匹配不上的第三形态——实测踩过，会造成同文档两条条目）。

### 7.2 P0-A 应调用的写入口

| 时机 | 调用 | 语义 |
|---|---|---|
| 改名/移动完成（磁盘已改名） | `index.registerDoc({ docKey, relPath: newRelPath, name: newName, scopeId, persisted, sourceRef })` | 只改身份与显示名，**不推进任何时间** |
| 改名/移动前若曾打开 | 无需额外调用 | `openedAt` 保持，改名不改变「最近」次序 |
| 另存为到新路径 | 新 `docKey` + `registerDoc`；旧条目不自动删（DS-10 由主控决定删除时序） | 收藏是否跟随由 P0-A 决定（本包不提供自动迁移，避免猜归属） |

### 7.3 必须遵守的三条纪律（否则会破本包不变量）

1. **不得绕过 `DocIndex` 直接 `localStorage.setItem('mindcanvas.docindex.v2', ...)`**：
   直写会跳过降级投影，旧版本立刻读不到新数据（破坏 R-B）。
2. **不得用 `relPath` 当身份**：改名后收藏会丢（这正是本包要修的问题）。
3. **不得在无归属证据时按「唯一同名」绑定旧记录**：绑定必须留下
   `relinkEvidence: { at, via: 'user-confirmed' }`（§6.2.1）。P0-A 若需要「按路径找条目」，
   用 `index.listDocs().find(e => e.relPath === p)`，**不要**在命中失败时创建新身份。

### 7.4 部分成功（源写成、删源失败）时的建议

P0-A 在部分成功（目标写成、删源失败）时**先**把索引的 `relPath` 更新为**目标路径**
（而不是保持旧路径），否则「最近」里的条目点击会指向已不存在的文件。
本包不提供 `rebindDestination`（属 P0-A 范围），但 `registerDoc` 可幂等重复调用，
且改名/移动不推进任何时间戳（`openedAt`/`savedAt` 均由 P0-A 用 `openDoc`/`saveDoc` 显式推进）。
