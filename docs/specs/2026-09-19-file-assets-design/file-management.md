# 文件管理增强设计（D1）

任务：FILE-ASSETS-DESIGN。日期：2026-09-19。依赖：`shared-contracts.md`（身份与接口）。

**范围声明**：文件树、搜索、最近、收藏、新建/改名/删除、拖入目录、右键菜单、面包屑、磁盘/浏览器双模式**均已存在**（见 `current-state.md` §2.1）。本文件只设计**增强与缺口**，不把既有实现重新列为从零建设。

---

## 1. 目标与不目标

**目标**：用户找得到文件、知道保存在哪里、改名/移动后仍能可靠保存、知道哪一份是当前正在编辑的。

**不目标**：不做云同步、不做版本历史、不做全文检索服务、不重写既有树/搜索/收藏的实现、不引入第二套清脏或离开逻辑。

| 项 | 内容 |
|---|---|
| 现状 | 【已有】点击文档行 → `onOpenFile(wsFile)`；兼容条目有 source → `applyDoc`，无 source → 转「重新选文件」（`FileManagerTree.tsx:155-163`；`FileManagerModal.tsx:76-96`） |

### 3.3 改名（文件名 vs 文档内部标题）

| 项 | 内容 |
|---|---|
| 现状 | 【已有】右键「重命名」→ 内联输入 → `renameFile(node.wsFile, name)`（`FileManager.tsx:212-223`）；实现为「读旧内容 → 建新文件 → 删旧」（`directoryHost.ts:308-318`） |
| 现状缺口 | 返回值（含新句柄/新路径）被丢弃（R-01）；当前文档改名后会话目的地不变 |
| 【新增】前置校验 | 目标名不得为空、不得含 `/`、不得含控制字符；与源同名（大小写完全一致）→ 直接取消，零 I/O；仅大小写差异 → **拒绝**（理由见下）；目标已存在 → 走 §5.2 冲突策略（不静默加序号） |
| 【新增】当前文档改名的编排 | 走 `shared-contracts.md` §3.2 的重绑状态机，**第一步是取操作租约**：`beginExclusiveOp('rename', target)` → 等 `waitForIdle` 且 `physicalWritesInFlight === 0` → 要求一次 `saved && current`（否则提示先保存）→（编辑继续，写入被租约挡回 `blocked`）→ `renameFileSafe` → `rebindDestination(newHandle, newRelPath)` → 更新 `workspacePath` / 索引（按 `lineageId` 迁移收藏与最近）→ 条件释放租约（`finally`，仅当 `leaseId` 仍是自己的）→ 若仍 dirty 立即重排一次 auto（写新目的地） |
| 【新增】为什么不能只清定时器 | 「取消 auto 定时器 + `waitForIdle`」**不是互斥**：内容再变化会重新排定 auto（`useAutoSave.ts:121` 的 deps 含 `content`），而 `waitForIdle` 只覆盖当前会话。竞态为「等待空闲 → 新保存进入 → 复制旧快照 → 删源」。租约是唯一能关闭它的机制（`shared-contracts.md` I-16…I-19） |
| 【新增】租约期间用户的观感 | 编辑照常（不冻结输入、不影响 IME/草稿）；若此时按 Ctrl+S，会收到「正在处理上一步操作」类提示且**不发起写入**；释放后 dirty 会被自动补写。详见 `shared-contracts.md` §3.5.4 的时序表 |
| 【新增】文件名 vs 内部标题规则 | **不自动同步**。改名只改文件名，不动文档首个 H1。完成后的提示里带一句「文档内的标题未改动」，并提供「同步标题」后续动作（P1 切片，见 §7）。反向（改标题 → 是否改文件名）同样**不自动**，理由：标题可能是文案、也可能重复，用它当文件名会产出非法/重复路径 |
| 【新增】仅大小写差异的处理 | 拒绝并说明：『浏览器的文件接口没有原地改名能力；在大小写不敏感的磁盘上，「Note.mm.md」与「note.mm.md」会被视为同一个文件，无法用「复制后删除」实现。请用系统文件管理器改名，或改成不同的名字。』——**不静默生成「note 2.mm.md」**（当前 `uniqueName` 会这样做，`directoryHost.ts:352-365`） |
| 【新增】失败 | 保留原名与原目的地；提示区分「权限被拒」（可重试 / 重新授权）与「磁盘不可用」（重试 / 重新选择文件夹） |

## 4. 删除当前文件或其父目录（F2 设计）

必须同时处理三件事：**草稿/组合输入**、**未保存模型**、**在途写入**。

```text
用户点「删除」（对象 = 当前文档 或 包含当前文档的目录）
        │
        ▼
  ⓪ 取操作租约：beginExclusiveOp('delete', target)
        ├─ refused('busy-lease')     → 提示『正在处理上一步操作』，零副作用
        ├─ refused('busy-physical')  → 提示『上一份写入还没有结束，请稍后重试』，零副作用
        └─ granted → 后续每个 await 后复查 leaseId / sessionToken / scopeId / opSeq
        ▼
  ① 草稿提交：flushEdits()（复用离开决策器的同一通道；draftFlush.ts:89-113）
        ├─ 'composing' → 暂缓：提示『输入法正在输入，请先结束输入』，等 compositionend 后自动续跑
        └─ 'failed'    → 保留草稿，中止删除，提示可修正后重试
        ▼
  ② 在途写入：本租约期间写入已被挡回，故此处只需确认 isSaving() 为假
        （若在取得租约前已有写入，取得租约时已被 busy-physical 拒绝）
        ▼
  ③ dirty 判定（getter，非快照，useUnsavedTransition.ts:348-355 同规）
        ├─ 不脏 → 进入 ④
        └─ 脏   → 三选：『保存后删除』/『放弃修改并删除』/『取消』
        ▼
  ④ 确认条（显示对象名 + 是否当前文档 + 不可撤销声明）
        ├─ 取消 → 零副作用；当前文档、草稿、目的地全部不变；面板保持
        └─ 确认 → 执行删除
                   ├─ 成功 → 关闭当前文档 → 回到启动页/空白态；索引移除条目（保留 legacyKeys）
                   └─ 失败 → 保留当前文档与目的地；错误提示 + 重试
        ▼
  ⑤ finally：条件释放租约（仅当 leaseId 仍是自己的）
```

**明确定义的边界**：

- 【决策】『放弃修改并删除』= 用户**显式**放弃。此分支下不得再自动保存（复用 `suppressPendingAuto()`，`DocumentLeavePort:82-85`），且删除后文档进入「已关闭」而非「未保存状态」——不能再出现一个指向已删文件的 dirty 会话。
- 【决策】删除后是否有「撤销」：**设计者建议不提供**（DS-13，待确认）。理由：真正的原子撤销需要把内容留在内存并重建文件，属于新能力且容易与「未保存」语义混淆。替代方案是 §3.6 的「改为归档」——但归档**依赖 P0-A 的可靠移动**，移动未落地前不得把归档当作已有补救路径（UD-3）。
- 【边界】在途写入已经发出且属于**被关闭会话**的物理 I/O 无法撤回；`waitForIdle()` 只保证**当前会话**已开始的 I/O（`useDocumentSaveSession.ts:146-157`）。租约新增的 `physicalWritesInFlight` 计数把这条边界变成可判定的拒绝（`shared-contracts.md` I-17），但仍**不能**撤回已发出的 I/O，因此文案不得承诺「磁盘上不会再有写入」。
- 【边界】删除父目录时，若目录内**还有其他正在被引用的资产**，提示追加『目录内的 assets/ 图片也会一并删除』（资产目录通常在同级或子级，见 §5.5 与 `asset-library.md` §5）。


### 5.3 移动部分成功

```text
拖拽「架构.mm.md」到 📁 归档  ——  部分完成
┌──────────────────────────────────────────────────────────────┐
│ ⚠ 已在新位置创建「归档/架构.mm.md」，但原文件删除失败。          │
│   现在磁盘上有**两份**：                                       │
│     • 归档/架构.mm.md（新，当前编辑的是这一份）                 │
│     • 研发/架构.mm.md（旧，仍占用原名）                         │
│   原因：没有删除权限。                                          │
│                                                              │
│   [重试删除原文件]  [保留两份]  [撤销新副本]     [稍后处理]      │
└──────────────────────────────────────────────────────────────┘
```

- **当前目的地**：**新文件成为当前目的地**（用户的目标就是「把它放到那里」，且已成功写出）。旧文件标为「待处理」，不参与会话写入。
- `[重试删除原文件]` → 只重试 `removeEntry`，**不重做复制**（防止覆盖新副本内容）。**删除前必须复查源是否被外部修改**：比对操作开始时记录的 `{ size, lastModified }` 快照；不一致 → **不删**，转为「保留两份」并提示『原文件已被外部修改，未删除』。
- `[撤销新副本]` → **有条件**：若副本已被继续编辑（`dirty`）或已被写入（`savedAt > opStartedAt`）→ **拒绝直接删除**，改为提示『这份副本已有新的改动，删除会丢失它们』并只提供「放弃这些改动并删除副本」或「保留两份」。未编辑未写入时，删除刚创建的新文件，目的地与路径回到旧位置；若撤销本身失败 → 明确提示「两份都在，请手动处理」。
- `[保留两份]` → 会话留在新位置；旧文件进入「需要处理」状态（树内标 `⚠ 重复`，提供「删除旧文件」入口；删除前同样走上面的外部修改复查）。
- `[稍后处理]` → 关闭提示；该条进入「待处理」清单（面板底部的『N 项待处理』），**不自动重试**。

## 6. 搜索 / 筛选 / 排序 / 键盘 / 拖放 / 无障碍

| 维度 | 现状 | 提案 |
|---|---|---|
| 搜索范围 | 前端过滤当前树（`FileManager.tsx:152`；`fileTreeModel.ts:148-168`），命中文档保留祖先链、命中目录保留子树 | 保留算法。**明示范围**（当前范围名）；新增搜索「文档内部标题」（需索引层 `title`，只对已索引文档生效，文案注明『仅搜索已记录的文档』） |
| 命中跳转 | 无 | 命中项高亮 + 「N 项匹配」计数；`Esc` 清空 |
| 筛选 | 视图 Tabs | 新增可选筛选：①「只看未保存/有改动」②「只看失联/待处理」。两者都基于已有状态，不做新的扫描 |

| 键盘导航 | 现状：树行为按钮（可 Tab 到），无方向键 | 【新增】roving tabindex：`↑/↓` 移动、`→` 展开、`←` 折叠或回父级、`Home/End` 首尾、`Enter` 打开、`F2` 改名、`Delete` 删除、`Esc` 关面板。焦点在重命名输入框内时全部让位给输入 |
| 上下文菜单 | 点击 window 关闭（`FileManagerContextMenu.tsx:30-34`），4 项 | 【新增】`Shift+F10` / 菜单键唤出；菜单 `role="menu"`、项 `role="menuitem"`、方向键移动、`Esc` 关闭并回焦触发项；新增「创建副本 / 移动到… / 重新定位 / 在系统文件管理器中显示（若平台支持，否则不显示该项）」 |
| 拖放反馈 | 经过目录高亮（`FileManagerTree.tsx:55-60`），无落点提示文案 | 【新增】拖起后顶部提示条：『拖到 📁 文件夹即可移动』；非法落点（同目录/后代）显示 🚫 且不响应；拖到面板空白 = 取消；拖动取消（Esc）恢复 |
| 无障碍 | 行是 `button`，星标有 `aria-label` 类文字（`FileManagerTree.tsx:132-154`） | 【新增】树容器 `role="tree"`、行 `role="treeitem"` + `aria-level`/`aria-expanded`/`aria-selected`；当前文档 `aria-current="true"`；重命名输入 `aria-label`；状态条 `role="status"` 用于保存中/失败提示；线框与配色保持既有 `CHROME` token |
| 触控 | 未验证 | 明确标注：拖拽在触控设备上未验证，不承诺（人工验收项） |
| **批量操作** | 无 | **不进入首期**（见下论证） |

**批量操作不进入首期的论证**：

1. 批量删除/移动的失败语义是 `partial` 的幂集——一次操作可能得到「N 成功 / M 部分成功 / K 失败」的混合结果，UI 与回执设计成本远高于单条。
2. 批量操作会横跨「当前文档」判定（多个对象里恰好包含当前文档），需要与离开决策器逐项交互，容易与单请求互斥（`useUnsavedTransition.ts:277`）产生新的悬挂态。
3. 现有树没有多选模型（`FileManagerTree.tsx` 无 selection 集合），需要新增选择态、范围选择、焦点与可访问性语义，属于独立切片。
4. 真实需求集中在「删除一批过期草稿」「把一批文档移入归档」。建议先以**单条 + 归档动作**（§3.6 的「改为归档」）覆盖最高频路径，再评估是否值得引入多选。
