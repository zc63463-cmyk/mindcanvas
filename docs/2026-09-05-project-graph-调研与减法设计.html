它对纯文本的态度（关键判断）

做到了
  • Markdown / Mermaid / 纯文本 / SVG / PNG 双向导入导出，是真能用
  • 粘贴纯文本自动建节点并智能识别：SVG 串 / URL / [text](url) / 绝对路径 / 超 3000 字→details

没做到
  • 节点标题在画布上是纯文本，不解析 Markdown
  • details 是 PlateJS 富文本，但画布上只当多行纯文本画——格式在画布丢失

判断

文本是它「输入 / 输出 / AI / 剪贴板」的一等公民，但不是「人类可编辑的事实源」。这正是 mindcanvas 与它最根本的分野——也是 mindcanvas 最难被抄走的部分。

P01 小时 · 0 代码

该做的不是造 CLI，是写一份契约说明（1 页文档），让 Agent 知道怎么写才不破坏往返无损。

守则必须写清的三个坑（都是本项目真实踩过的）：① 标题下直接写描述（W-STRAY-LINE）第一次解析就丢；② 空行必须插在笔记块之前（笔记归属其后的节点）；③ 分支之间保留一个空行。违反这三条，往返仍报"无损"但内容已丢。
G2

视口裁剪

P10.5–1 天

现状：MapView.tsx 渲染全部 layout.nodes，grep 全仓无 cull / viewport 裁剪。

做法：① viewport.ts 已有 ViewportController 与 transform，补 coverWorldRect(frame, transform)；② 渲染循环前过滤 nodes.filter(n => intersects(n.box, cover))；③ 保留 1 屏缓冲（PG 无缓冲，快速平移会露白）。

三条硬约束：① 裁剪只影响渲染，不能影响布局——布局必须全量，否则树会散；② 边要单独判断：两端点都在视口外但边穿过视口的情况必须保留，要用边的包围盒判，不能用两端点；③ lodFor(scale, nodeCount) 的 nodeCount 应改用可见节点数而非总数。
G3

粘贴即建节点

P10.5 天 · 需你拍板语义

现状：MapView.tsx:780 的 onPaste 只处理 clipboardData.files（图片），文本分支缺失。

待你决策——多行文本粘进来建什么？

方案语义适合
A 缩进感知按缩进 / Tab 层级建子树从大纲粘贴
B 平铺兄弟每行一个兄弟节点从列表粘贴
C 单行即节点多行才走 A，单行直接建一个推荐：行为可预测
PG 的做法是「整段进一个节点的 details」——那是自由图的语义。树工具应该让多行展开成结构，这才是纯文本思维导图的本分。
另：必须走 controller 的 pushHistory（现有 History<T> 55 行，limit=100），保持不可变树语义。

反面教材：从 PG 身上学到的三件事

它做对的我们抄，它长歪的地方更要记住——因为那正是 20k 行项目未来的样子。

1

单文件 4,538 行是危险信号

shortcutKeysRegister.tsx 一个文件塞了 347 条快捷键。这不是"功能丰富"，是拆分失败的证据。

这面镜子照的是 mindcanvas 的 MindmapStage.tsx（1,573 行）。拆分已有进展（从 1,741 降到 1,573，−9.7%），别停在这里。剩余两块：玻璃翻卡（约 107 行，依赖 8 个 props）、主函数交互层。
2

"分两批初始化服务"是脆弱信号

loadAllServicesBeforeInit 与 loadAllServicesAfterInit 的存在（后者专门延迟注册 HistoryManager、CollaborationService），说明依赖关系已经复杂到需要人工排序。

这是架构开始失控的早期征兆，却被当成"成熟的设计"写进代码。mindcanvas 别引入服务层——现在的 edit/controller.ts 单文件（11.5KB）完全够用，不要为了"看起来专业"而加 DI。
3

死代码和空文档会一直留在仓库里

vditor-panel.tsx 是全仓库零引用的 Markdown 编辑器组件，仍在代码中；根目录 TODO.md 是 0 字节空文件。

这就是为什么项目铁律第一条是「别信文档里的状态描述，规划前先 grep 源码确认」——文档和代码都会腐化，而且腐化得悄无声息。PG 的 README 也没写它的存储是二进制，那是读源码才知道的。
最后一句

mindcanvas 用 1/5.6 的代码换来了 15 倍的测试密度、独家避障路由和 Agent 原生可读的事实源。这次调研最大的收获不是"该加什么"，而是确认了哪些东西不必加。
