结论先行

  • 当前形态：「元数据索引」+「最近列表」两堆独立 localStorage；UI 是一个非单态浮层；.mm.md 才是事实源。
  • 核心取舍：库里只有最近 8 条文档保留内容快照，更早的只剩元数据，打开需重新选文件。
  • 建议路径：① 先修 P0 ② 合并为单一事实源 ③ 8 条上限在 UI 显式化 ④ 目录保持虚目录，不做实体化。
  • 暂缓：升级 IndexedDB、目录实体化 —— 等 friction-log 触发反转条件再动。

发现 2 · rename 只改显示名，id 不变

{"id":"b.mm.md","name":"新名字",...}

表面看是"失配"，但有 source 快照兜底，短期仍能打开。真正的问题在没有 source 的旧条目：名字改了、磁盘文件名没改，用户再也找不到对应关系。

发现 3 · 容量策略的真实形态（最关键）

指标实测值
库内文档总数12 条
仍带内容快照的8 条（仅最近 8 条 d5–d12）
每条 source 体积约 1.2 KB（400 字中文）
12 条总占用约 10.4 KB
SOURCE_KEEP = 8 是硬约束：超过 8 条的文档只剩元数据，点击打开会走"重新选择文件"。
即：文档数 > 8 之后，文件库实质上退化成「最近 8 个可直接打开的 + 一堆需重新定位的快捷方式」。

P1 两堆 localStorage 各说各话

schema 独立、容量策略独立、互不通知。同一份文档在两处都有记录，重命名/删除只影响其中一处 → 两边状态漂移。

P1 只有 8 条能直接打开

见取证发现 3。这是容量策略的必然结果，不是 bug，但是设计上的取舍 —— 需要明确是否接受。

决策 A · 存储后端是否升级

成本项维持 localStorage升级 IndexedDB判定
解除 8 条上限✗✓差异项
重写持久化层—中（异步 API，调用点全变 async）差异项
迁移旧数据—小（读一次写入即可）差异项
UI 改造两方案都要做共担
打开守卫（P0）两方案都要做共担
推荐：先不动后端，只把 8 条上限显式化。
目前没有证据支持"文档数 > 8 且有必须直接从库里打开的强需求"。
反转条件：friction-log 出现「想打开第 N 个历史文档却要重新选文件」≥ 2 次，立刻升级。

决策 B · 目录是否实体化

成本项虚目录（现状）实体目录
建空目录✗✓
目录重命名级联无（不存在）高（要改写全部后代 folder）
删除目录语义无要定义（级联删？提升子级？）
推荐：保持虚目录。当前"目录 = 路径推导"足够支撑层级浏览，实体化换来的是「建空目录」这个低频需求，代价是一整套级联语义。
反转条件：出现「我想先建好目录结构再往里放文档」的真实需求。

决策 C · 两堆存储是否合并

推荐：合并为单一事实源（DocLibrary 唯一入口，recent 从它派生：list() 按 ts 排序取前 8）。

成本小（新增方法 + 改几处调用），收益是消除状态漂移。代价：recent 存的是 MindDoc（含 saved 等业务字段），DocEntry 没有 —— 合并时要补字段或做映射，需谨慎。

诚实披露

  • 取证基于 jsdom 模拟的 localStorage，未覆盖真实浏览器的配额触顶行为（5MB 是注释里的经验值，未实测）。
  • 「升级 IndexedDB」的成本是架构级判断，未做原型验证；真要做时建议先写 30 行读写原型。
  • 决策 B（不做目录实体化）是判断而非实证。如果你预期会大量使用"先建结构再放文档"的工作流，这个结论应该反过来。
