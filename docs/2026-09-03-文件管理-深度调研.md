# 文件管理 · 深度调研与设计建议

> 日期：2026-09-03 · 方法：分层 Explore agent + 逐条交叉验证 + jsdom 运行时取证
> 所有结论均附 `文件:行号`；量化数据来自实际跑出来的存储，非估算

---

## 结论先行

| 判定 | 内容 |
|---|---|
| **当前形态** | 「元数据索引」+「最近列表」**两堆独立 localStorage**；UI 是一个非模态单态的浮层；文档内容 `.mm.md` 才是事实源 |
| **P0（会丢数据）** | **切换文档时未保存修改被静默丢弃** —— 三处打开入口中两处没有守卫 |
| **核心设计取舍** | 库里**只有最近 8 条文档保留了内容快照**，更早的只剩元数据，打开需重新选文件 |
| **建议路径** | ① 先修 P0（半天）② 合并为单一事实源 ③ 存储后端升级解除 8 条上限 ④ 目录**保持虚目录**，不做实体化 |

一句话：功能骨架是完整的，但**「打开」这条最基础的路径存在数据丢失风险**，且容量策略会让文件库在超过 8 个文档后退化成"最近使用列表"。

## 一、分层实证

### 1.1 数据层：`DocLibrary`（元数据索引）

| 项 | 事实 | 证据 |

## 二、运行时取证（jsdom 实测，非读代码猜）

用一个临时探针实跑 `DocLibrary`（跑完已删除），结果：

```
【folders】             ["工作","工作/项目"]
【childrenOf 工作】      {"dirs":["项目"],"docs":[]}
【childrenOf 根】        {"dirs":["工作"],"docs":[{...a.mm.md}]}
【rename 后 get(id)】    {"id":"b.mm.md","name":"新名字", ...}
【存储原文】             [{"id":"b.mm.md","name":"新名字",...,"source":"# b"}, ...]
```

**发现 1：目录树逻辑本身是健康的。** 深层路径 `a/b/c` 能正确逐级推导，脏路径 `' 工作 //项目 '` 会被 `cleanFolder` 清洗为 `工作/项目`。

**发现 2：`rename` 只改显示名、`id` 不变。** 表面看是"失配"，但因为有 `source` 快照兜底，短期仍能打开 —— 真正的问题在**没有 source 的旧条目**：名字改了、磁盘文件名没改，用户就再也找不到对应关系了。

**发现 3（最关键）：容量策略的真实形态。**

| 指标 | 实测值 |
|---|---|
| 库内文档总数 | 12 条 |
| **仍带内容快照的** | **8 条**（仅最近 8 条：d5–d12） |
| 每条 `source` 体积 | 约 1.2 KB（400 字中文） |
| 12 条总占用 | 约 10.4 KB |

→ **`SOURCE_KEEP = 8` 是硬约束**：超过 8 条的文档只剩元数据，点击打开会走"重新选择文件"。
即：文件库在文档数 > 8 之后，实质上退化成了「最近 8 个可直接打开的 + 一堆需要重新定位的快捷方式」。

## 三、缺口清单

### P0 · 切换文档会静默丢未保存修改 🔴

`applyDoc` 有守卫：

```ts
if (controller.dirty && !window.confirm('当前文档有未保存的修改，确定放弃并切换？')) return;
```
— `useDocumentActions.ts:43`

但**三处打开入口行为不一致**：

| 入口 | 实现 | 守卫 |
|---|---|---|
| 文档栏「最近」菜单 | `applyDoc(d)`（`MindmapStage.tsx:1202`） | ✅ 有 |
| 工具栏「打开」 | `applyDoc(...)`（`:1059`、`:1231`） | ✅ 有 |
| **FileManager 点击文档** | **直接 `setDoc({...})`（`:1578`）** | ❌ **无** |
| **启动页「最近」** | **直接 `setDoc(d)`（`StartupScreen.tsx:205`）** | ❌ **无** |

→ 从文件管理器或启动页切换文档，未保存的修改**连提示都没有**就直接没了。这是当前最严重的缺陷，且与「文件管理」这个功能的入口强相关。

### P1 · 两堆 localStorage 各说各话

`mindcanvas.library.v1`（全量元数据 + 8 条快照）与 `mindcanvas.docs.v1`（最近 8 条）**schema 独立、容量策略独立、互不通知**。
同一份文档在两处都有记录，重命名/删除只影响其中一处 → 两边状态漂移。

### P1 · 只有 8 条能直接打开

见取证发现 3。这是容量策略的必然结果，不是 bug，但是**设计上的取舍**，需要明确是否接受。

### P2 · 交互缺失

| 缺口 | 证据 |
|---|---|
| 移动靠手填路径文本，无拖拽、无目录选择器 | `FileManager.tsx:192-210` |
| 无文件名搜索（画布 `Ctrl+F` 只搜节点） | — |
| 新建后落到根目录，不能建时选位 | `FileManager.tsx:217` |
| 「移除」只删索引、无撤销/回收 | `FileManager.tsx:220-231` |
| 无目录实体：不能建空目录、重命名目录、删除目录 | `docLibrary.ts` 无对应 API |

## 四、设计方案与成本量化

### 4.1 三个决策点

#### 决策 A：存储后端 —— 是否从 localStorage 升级

| 成本项 | 维持 localStorage | 升级 IndexedDB | 判定 |
|---|---|---|---|
| 解除 8 条上限 | ✗ | ✓ | **差异项** |
| 需重写持久化层 | — | 中（异步 API，全部调用点变 async） | 差异项 |
| 迁移旧数据 | — | 小（读一次 localStorage 写入即可） | 差异项 |
| UI 改造 | — | **共担**（无论选哪个都要改 UI） | 不构成劣势 |
| 打开守卫（P0） | **共担** | **共担** | 不构成劣势 |

**注意共担成本**：P0 守卫和 UI 改造在两个方案里都要做，不能算到"升级 IndexedDB"头上。

**推荐**：先不动后端，只把 8 条上限**显式化**（UI 上标明"仅最近 8 个可直接打开，其余需重新选择"）。
理由：文档数超过 8 个且有"必须直接从库里打开"的强需求，目前**没有证据支持**——这属于 F 自用周还没产生足够摩擦的领域。
**反转条件**：friction-log 出现「我想打开第 N 个历史文档却要重新选文件」≥ 2 次，立刻升级。

#### 决策 B：目录是否实体化

| 成本项 | 虚目录（现状） | 实体目录 |
|---|---|---|
| 建空目录 | ✗ | ✓ |
| 目录重命名级联 | 无（不存在） | **高**（要改写全部后代的 folder） |
| 删除目录语义 | 无 | 要定义（级联删？提升子级？） |
| 数据模型改动 | — | 新增实体 + 迁移 |

**推荐：保持虚目录。** 当前"目录 = 路径推导"足够支撑层级浏览，实体化换来的是「建空目录」这个低频需求，代价是一整套级联语义。
**反转条件**：出现「我想先建好目录结构再往里放文档」的真实需求。

#### 决策 C：两堆存储是否合并

**推荐：合并为单一事实源**（`DocLibrary` 作为唯一入口，`recent` 改为从它派生：`list()` 按 `ts` 排序取前 8）。
成本小（新增方法 + 改几处调用），收益是消除状态漂移。
**代价**：`recent` 目前存储的是 `MindDoc`（含 `saved` 等业务字段），`DocEntry` 没有 —— 合并时要补字段或做映射，需谨慎。

### 4.2 推荐执行顺序

| 顺序 | 事项 | 量级 | 理由 |
|---|---|---|---|
| 1 | **修 P0：三处入口统一走 `applyDoc`** | 半天 | 会丢数据，且改动极小（两处 `setDoc` → `applyDoc`） |
| 2 | 合并两堆存储为单一事实源 | 1–2 天 | 消除漂移；但要先补齐 `DocEntry` 缺失字段 |
| 3 | 8 条上限在 UI 上显式化 | 半天 | 让取舍可见，而不是让用户撞上才知道 |
| 4 | 交互补全（拖拽/搜索/建时选位） | 2–3 天 | 等 F 周摩擦排序后再做，别提前投资 |
| — | ~~升级 IndexedDB~~ | — | **暂缓**，等 friction-log 触发反转条件 |
| — | ~~目录实体化~~ | — | **不做**，代价大于收益 |

## 六、诚实披露

- 本报告的取证基于 jsdom 模拟的 localStorage，**未覆盖真实浏览器的配额边界行为**（5MB 是注释里的经验值，未实测触顶）。
- 「升级 IndexedDB」的成本估算是架构级判断，未做原型验证；真要做时建议先写一个 30 行的读写原型。
- 决策 B（不做目录实体化）是我的判断，**如果你预期会大量使用"先建结构再放文档"的工作流，这个结论应该反过来**。
