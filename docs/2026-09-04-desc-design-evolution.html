根本问题 desc 与 qa 是两套重叠机制

规格书写得很清楚：desc（常驻说明）与 qa（快速注释，按需展开）是两套并存机制。 但它们本质上做的是同一件事 —— 在节点下方显示额外文本。

desc（描述）qa（快速注释）
内容形态一段纯文本（多行）问答条目列表
显示位置节点下方节点下方
触发方式点描述块 / 点节点（放大）点节点
占布局是（16 行软上限）是（固定注释区高）
实现DescBlock + DescOverlays GrowthCommentPanel + ExpandCommentOverlay

后果：两套各自维护"从盒底往上锚"的逻辑，改了其中一套的高度构成， 另一套就会压上来 —— 今日修的 P0-2 正是这么产生的。这不是偶然 bug，是结构性重复。

次要问题 收缩一行与「换行可见」的张力

原始设计要"默认收缩一行"，你实际使用中要"注释换行可见"。 于是展开上限被一路抬高：6 → 12 → 40 → 16。每次调整都是在两者之间重新找平衡点， 但底层的"收缩一行"从未被质疑过。

三个调整方向

A · 合并 desc 与 qa 为「节点附属内容」

统一数据模型与渲染，用类型字段区分（说明 / 问答）。

成本项判定
协议变更差异项 —— 需迁移既有 .mm.md（或保留 desc/qa 双字段兼容）
消除结构性重复唯一占优项 —— 从此只有一处算"盒底往上锚"
UI 改造共担 —— 三个方向都要动 UI

代价：动协议，风险最高；且幕布语义里 desc 与 qa 确实是两种东西， 强行合并可能丢失表达力。反转条件：若你始终把二者当同一种"补充说明"用 → 该合并。

B · 保持两套，但抽出公共的「附属区栈」

把它们抽象成节点下方的纵向栈：rect 之后依次排 desc、qa，各自声明高度， 由一个统一的布局函数负责分配位置。谁先谁后可配置。

代价：不解决模型重复，只是把"重叠"从 bug 变成架构上不可能。 反转条件：若 desc 与 qa 在你心里是两种不同东西 → 选这个（改动最小）。

C · 不改模型，改交互：把「更多内容」移出画布

节点上只留一行摘要，点击后在侧边面板（已有 SidePanels 互斥单态）或 浮层卡片里看完整内容，画布上的节点不再被撑变形。

代价：与"让树变形、上下挤压"的需求相反 —— 这是你明确要过的功能。 反转条件：若挤压后观感仍不理想（比如节点密时太乱）→ 回到这个方向。

我的判断（已根据 qa 的历史修正）

原本我推荐 B（只抽公共附属区栈、不动模型）。但翻出 qa 的三版演变之后， 推荐改为 A —— 理由不是"它们相似"，而是：

它们已经被各自的历史推到了同一个终点。qa 在 08-28 就否掉了浮出和 popover， 选择了占布局挤压 + 换行完整显示；desc 在 09-03 用四次返工走了同样的路，最后也是占布局挤压 + 换行。 现在两套代码在做完全相同的事，只是数据结构不同（一段纯文本 vs 问答条目列表）。

继续留着两套，我们今天修的"重叠"只是第一个代价 —— 以后任何一边调整高度构成， 另一边还会再压上来一次。

稳妥的走法：先做 B（把重叠封死），再在 B 的统一栈之上合并数据模型 —— B 是 A 的安全中间步骤，不是二选一。

C 先不做：它是你上次明确否掉的方向（你要的就是挤压）。
