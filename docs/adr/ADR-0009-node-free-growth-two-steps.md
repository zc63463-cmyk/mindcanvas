# ADR-0009: 节点自由生长（方向分叉 + 自由坐标）两步走

## Status

Accepted（2026-09-06，grill-with-docs 与用户逐条对齐后）

## Context

用户提出「PG（project-graph）式自由生长」需求，并在浏览器验收时发现：D 包（`note.dir`
方向分叉）的 `layoutMindmapBranched` 与 `collectExplicitDir` **只有定义与导出、零调用点**——
菜单能写 `note.dir`，但渲染管线不消费它，界面无任何变化。测试 80/680 全绿、变异验证通过，
却全是**孤立函数**证据，属于假交付。

根因：验收标准只验证「函数正确」，未验证「管线真的调用了它」。

领域事实（`docs/2026-09-05-project-graph-调研与减法设计.md` §9.9c，grep 实证）：

- PG 的「自由生长」本质是**白板坐标**（节点有坐标、可拖到任意位置）；方向分叉只是其
  树布局算法的副作用。二者不是一回事。
- 文档自陈 mindcanvas 的「节点自由移动 ❌ 唯一短板」；G7（节点自由坐标）设计已被
  「自由边的 manual 机制」完整验证，预估 2–3 天。
- 文档 §9.6 的推进策略：先做多中心（已由布局岛 A1–A6 完成）验证「用户到底需不需要
  自由摆放」这个最大假设，再决定是否投入 3–5 天做坐标。

新增变量：cid 子树稳定身份（C 包）已于同日落地——文档 §9.9c 原写「坐标必须也用路径锚」，
在 cid 存在后已不成立。

## Decision

**分两步，每步独立可验收：**

**第一步（本次）· 方向分叉接管线** —— 让已实现的 `note.dir` 真正生效：
同节点的子节点按各自声明方向挂到不同侧（思想分叉）。

接线点**两处**（缺一不可）：

1. `packages/react/src/demo/pipeline.ts` 无岛路径：`layoutMindmap` → `layoutMindmapBranched`
2. `packages/kernel/src/layout/forest.ts` 岛内路径：`LAYOUT_BY_DIR[spec.dir]` → 支持分叉的
   分支布局（注入 `islandDir = spec.dir`）

> 只接 pipeline 一处会导致「有布局岛时菜单无反应」——而岛是常用场景。

**第二步（后续）· 节点自由坐标** —— 拖动任意节点到任意位置，脱离自动布局。

- 持久化：**统一为一套文档级坐标层** `root.note.pos[path]`（与 `centers` 同级，节点不挂坐标）
- `centers` 职责收窄为「哪些节点是岛」，坐标统一由 `pos` 承担——避免出现两套坐标设施
- 锚定：**双轨，cid 优先 + 路径兜底**（与 C 包 `collectCenters` 同构；纯路径锚会让改名
  dangling 成为第二个历史包袱）
- 优先级：**坐标优先** —— 拖动即锁定，`dir` 对该节点失效；清空坐标恢复自动布局并重新
  遵循 `dir`（与文档 §9.4「拖动过的锁定，其余自动」一致）

**`note.dir` 保留节点级**（语义意图，先例 `via`/`edge`/`desc`/`qa`）：随子树切断/接回/
粘贴零迁移成本。与「坐标存文档级」不矛盾——语义意图挂节点，几何状态存文档层。

## Consequences

**变容易：**

- 第一步半天内可拿端到端可见效果，用来实证「用户是否需要自由摆放」，决定第二步是否值得投 2–3 天
- 坐标设施只有一套，岛坐标与树内坐标不会打架，优先级规则单一
- cid 双轨让改名/移动不再 dangling，与 centers 现有实现同构、心智负担低

**变难 / 代价（必须披露）：**

- **增量缓存**：`layoutMindmapBranched` 的分支路径为全量布局，忽略 `LayoutCache` 命中。
  无 `note.dir` 的旧文件仍走回退路径保留缓存；一旦文档中存在任意 `note.dir`，该文档布局
  失去增量缓存。当前分叉节点通常较少，判断可接受，但需在第二步前实测 2000 节点耗时不劣化
- 邻侧防叠是「布局期一次推开」而非迭代，三向以上复杂分叉可能残留重叠（已知取舍，见
  D4′ 验收项）
  > **2026-09-10 更新**：该取舍已消除。原「一次推开」被 `kernel/src/layout/separate.ts`
  > 的 `separateTree`（自底向上兄弟子树**刚体分离**，最小位移 + 方向偏好 + 硬堆叠兜底）
  > 取代，随机四向树实测重叠 87.5% → 0；`layoutForest` 的自动排列同时改为按真实
  > bounds 对齐右边界，四向生长的岛不再互相压叠（见 CHANGELOG 1.7.0）。
  >
  > **2026-09-11 更新（收敛期两处修正 + 术语澄清）**：
  > ① **落位期避让祖先链盒**：`layoutMindmapBranched` 的方向组落点基准 `occ` 并入
  >    「根 → 父」祖先链盒——left/up 组主动避开祖父盒，不再把「left 组落进祖父盒」
  >    留给事后外推处理（实测：外推 54~148px 会连带未声明方向的兄弟位移，破坏
  >    B″ 的局部性承诺）。
  > ② **出边走廊判定**：`clearParentEdges` 的越界判定由「整棵子树包围盒」改为
  >    `corridorSubtreeBox`（只统计真的落进「父 → 本节点」空隙走廊的盒）——保住
  >    「孙节点落在父右缘 ↔ 子左缘之间 → 整棵外推」的契约，同时不再误伤
  >    「绕过走廊生长的反向分支」。
  > ③ **术语澄清**：本 ADR 语境的「走廊」专指**出边走廊**（父与子之间的空隙）；
  >    `linkClear` 的折线包围盒为**路由走廊**、clamp 闸门的 rail 判定为**梁位带**。
  > 验收：typecheck 0 / 1418 用例全绿 / depcruise 0 / budget 持平（2026-09-11）。
- 第二步会引入坐标进 `.mm.md`，需遵守「只在用户拖动过时写入」以免反噬手写体验（文档 §9.7）

## 验收标准（第一步，端到端五条）

1. 浏览器实操可见（截图为证）
2. 保存重开保持
3. undo / redo 可回
4. 旧文件（无 `note.dir`）布局逐像素不变
5. **管线级测试**：断言渲染管线真的调用了分支布局，而非只测孤立函数

> 第 5 条是本次假交付的直接对策：测试必须覆盖「接线」，不只是「函数」。
