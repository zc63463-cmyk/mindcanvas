# 连线智能避障路由：算法调研与设计方案

> 日期：2026-08-31 · 触发：蒋指导反馈「连线不会智能避开节点，而是直接穿过，这是低级设计逻辑」
> 定位：调研 → 方案对比 → 设计。实现另起批次（见文末「落地拆分」）

---

## 一、问题定义

### 1.1 现状（代码定位）

`packages/react/src/render/freeEdges.ts` → `buildFreeEdgePath()`：

```ts
const p0 = borderPoint(a, bc.x, bc.y)   // 源盒边界交点
const p3 = borderPoint(b, ac.x, ac.y)   // 靶盒边界交点
const bow = len * curvature             // 恒定弓高（沿法向）
const c1 = p0 + d*0.35 + n ; const c2 = p0 + d*0.65 + n
```

即：**两端点间直接拉一条"带固定侧弓"的三次贝塞尔**，全程不感知路径上是否存在其他节点卡片。
弓高只与**边长**成正比，与障碍物无关 → 连线必然可能穿过节点。

### 1.2 学术界的定性：这就是被点名的反面教材

GD 2009 论文（Wybrow / Marriott / Stuckey，《Orthogonal Connector Routing》，libavoid 作者）开篇：

> "Most interactive diagram editors provide orthogonal connectors with some form of automatic connector routing. However, **these tools use ad-hoc heuristics that can lead to strange routes and even routes that pass through other objects**."

论文实测点名：
- OmniGraffle Pro 5.1.1、Dia 0.97 —— 自动正交路由**会与物体重叠**
- Visio 2007、ConceptDraw Pro 5 —— 能避障，但启发式不可预测（不最小化距离或段数）
- yFiles / yEd —— 有正交路由，但**编辑过程中不维持**

我们的"恒定法向弓高"正属于论文批评的 ad-hoc heuristic。**用户的判断是准确的。**

## 二、方案调研

### 2.1 学术方案：libavoid 三阶段（正交可见性图 + A\* + Nudging）

**出处**：`mjwybrow/adaptagrams`（Monash），Inkscape 连接器、Dunnart 使用，论文 GD 2009。

| 阶段 | 内容 | 关键性质 |
|---|---|---|
| ① 正交可见性图 | 两阶段扫描线（X 维扫描生成水平可见段 → Y 维扫描生成垂直可见段），断点处分裂并建 dummy 顶点 | 复杂度 **O((n+k) log n)**，n=顶点数，k=交点数 |
| ② A\* 寻路 | 在可见性图上搜索，代价 = `f(路径长度, 拐点数)` 单调函数 | **保证最优**：最小化长度与拐点的单调组合 |
| ③ 视觉整理 / Nudging | 共享线段上排布并推开各连线；尽量走"巷道"中线；让交叉发生在共享段首尾 | 消除不必要的线-线交叠 |

**工程特性**：
- 图是**静态**的，仅在「形状增删/移动」时重建，同一事务内所有连线复用 → 摊薄成本
- 顶点带"长程可见性标志"（`XL_CONN`/`XH_EDGE`…）预计算，用于 A\* 剪枝

**适配性判断**：
- ✅ 算法最优、可证明、工业验证
- ❌ C++ 实现，移植到 TS 约 2000+ 行（仅图构建就 650 行），且 nudging 阶段复杂度高
- ❌ **产出是刚性直角折线**，与思维导图"有机曲线"的审美冲突
- ❌ 无 npm 可直接用的 JS 移植

### 2.2 工业方案：`@tisoap/react-flow-smart-edge`（网格 A\* + 平滑）

定位：React Flow 生态里解决**完全相同问题**的生产库（353+ stars，TS 编写，MIT）。

| 机制 | 说明 |
|---|---|
| **网格 A\* / Jump-Point Search** | 将画布栅格化为 `Uint8Array`，节点矩形（外扩 `nodePadding`）标为阻挡格 |
| **`routeOnlyWhenBlocked`（默认开）** | **直线已通畅的边完全跳过寻路**，直接走原生路径 —— 典型图只有少数边真正需要 A\* |
| **Corridor cropping** | 每条边只在其**自身端点周围的走廊**内建小网格；失败才逐步扩宽，而非全图建网格 |
| **LRU 路由缓存** | 按各自障碍物集合缓存；移动一个节点只重算「走廊确实发生变化」的那几条边 |
| **Web Worker 批量路由** | 默认在 worker 线程批量计算，主线程不阻塞；节点先以原生路径绘制，路由完成后再替换 |
| **降级** | 找不到路 / 路由被推迟 → 回退原生路径，绝不空白 |
| **平滑分离** | `svgDrawSmoothLinePath` 把 A\* 网格折线转成平滑曲线；寻路函数与绘制函数可分别替换 |

**实测数据（库自带 bench）**：

| 项 | 提升 |
|---|---|
| 网格构建（typed array vs 旧对象网格） | **20–24×** |
| A\* 寻路 | **5.4×（对角）/ 9.8×（正交）** |
| Jump-Point Search | **6.8×** |
| 走廊裁剪网格（750 节点图） | 对比全图建网格约 **1.7×** |
| 750 节点 / 1125 边场景 | 节点瞬时绘制，首批路由在 worker 约 **2.2s** 完成 |

### 2.3 其他参照

| 方案 | 特点 | 评价 |
|---|---|---|
| **ELK (Eclipse Layout Kernel) orthogonal** | Java，分层布局的正交边路由工业标准 | 重，且与"用户手排节点"场景不同（ELK 会同时算布局，而我们布局已定） |
| **dagre / dagre-d3** | 有正交边路由，但耦合分层布局 | 同上，引入布局求解器触碰本项目红线 |
| **draw.io / mxGraph** | 内置多种 edge style（orthogonal / entity-relation / 曲线），避障靠自身 router | 闭源实现，参考价值在交互约定而非算法 |
| **yEd / yFiles** | 正交路由质量高 | 商业闭源 |

## 三、方案对比与选型

| 维度 | A. 正交可见性图 + A\*（libavoid） | **B. 网格 A\* + 平滑（推荐）** | C. 贝塞尔 + 局部绕行启发式 |
|---|---|---|---|
| 避障正确性 | ✅ 可证明最优 | ✅ 网格分辨率内正确 | ⚠️ 启发式，仍有穿模 |
| 产出形态 | 刚性直角折线 | **平滑曲线（可配圆角/直线）** | 曲线 |
| 与思维导图审美 | ❌ 冲突（像流程图） | ✅ 契合 | ✅ 契合 |
| TS 实现成本 | 高（~2000 行，含 nudging） | **中（~400–600 行）** | 低（~100 行） |
| 性能可控性 | 图重建 O((n+k)log n)，静态复用 | **走廊裁剪 + 按需寻路，成本近似按"受阻边数"计** | 最优（几乎零成本） |
| 可调参 | 少（最优解，无需调） | 网格比、padding、拐点惩罚 | 多（且都是魔法数） |
| 降级容错 | 需自行设计 | **有成熟做法（回退原生路径）** | 无 |
| 学术/工业背书 | GD 2009 + Inkscape | react-flow-smart-edge 生产验证 | ❌ 论文明确批评此类 |

### 选型结论：**B（网格 A\* + 平滑）**

理由（按权重）：

1. **审美一致性压倒最优性** —— 思维导图的产品定位决定连线应是有机曲线。A 的"最优直角折线"在思维导图上反而是审美倒退。B 的平滑输出与现有树边（三次贝塞尔）风格统一。
2. **成本/收益比** —— A 需移植 2000+ 行 C++ 并自研 nudging；B 约 400–600 行 TS，且**性能优化套路已被生产验证**（按需寻路 / 走廊裁剪 / LRU 缓存 / 降级）。
3. **增量式落地** —— B 的 `routeOnlyWhenBlocked` 意味着**大多数边行为完全不变**（直接连线通畅时沿用现贝塞尔），只在真正受阻时才付出成本，风险与回归面都最小。
4. **不触碰项目红线** —— 两者都不移动节点（非布局求解器），不违反「不引入力导向/迭代布局」的红线；纯函数无 DOM，符合 kernel/react 分层纪律。

> 保留 A 作为**后续可选增强**：若未来接入"外框/分区"等需要严格直角绕排的场景，可再评估正交路由。

## 四、详细设计（方案 B）

### 4.1 总体流程

```
⑤ 端点锚定 → ④ 平滑成曲线 →  ③ 路径简化/拉绳  → ② A* 寻路 → ① 快速通道判定
   borderPoint   圆角/样条     去共线+视线拉绳    网格8向      直线通畅？
                                                              └ 通畅 → 直接用现有贝塞尔（零成本）
```

### 4.2 ① 快速通道判定（`routeOnlyWhenBlocked`）

- 取源/靶边界点 `p0 → p3`，对**当前贝塞尔做粗采样**（如 16 点）得到折线
- 宽相位：只取与「边包围盒 + margin」相交的障碍盒参与测试（空间筛选，避免全量 O(N)）
- 任一采样点落入某障碍盒（含 `nodePadding` 外扩）→ 判定受阻，进入寻路
- **通畅 → 直接返回现有 `buildFreeEdgePath` 结果**

> 这一步保证：绝大多数边（实测预期 >70%）视觉与性能零变化，回归风险极低。

### 4.3 ② 走廊裁剪 + 网格 A\*

**走廊（corridor）定义**：`AABB(p0, p3)` 外扩 `corridorMargin`（初值如 200px）。

- 仅收集与走廊相交的障碍盒 → 候选障碍集通常是个位数
- 栅格化：格边 `gridRatio`（默认 12–15px），网格为 `Uint8Array`（1=阻挡）
- 障碍盒外扩 `nodePadding`（默认 14–20px）后标记阻挡格
- A\*：8 向，启发式用 **octile distance**；拐点惩罚 `turnPenalty` 抑制锯齿
- **失败则扩宽走廊重试**（×1.8，最多 3 轮）；仍失败 → 回退现有贝塞尔（降级，绝不空白）

### 4.4 ③ 路径简化（拉绳 / string pulling）

网格 A\* 输出是逐格点列，需压缩：

1. **去共线**：连续同向点只保留首尾
2. **视线拉绳**：对相邻三点 `i, i+1, i+2`，若 `i` 到 `i+2` 的直线段不与任何障碍相交 → 删除 `i+1`，迭代至收敛

目标：把数十上百个网格点压到 **3–7 个拐点**。

### 4.5 ④ 平滑成曲线

两种可选，建议**默认圆角折线**（更可控、与箭头/marker 兼容好）：

- **圆角折线**：每个拐点用二次贝塞尔/圆弧倒角，半径 `r = min(cornerRadius, 相邻段长/2)`
- **Catmull-Rom → 三次贝塞尔**：更"有机"，但可能轻微贴障（需把障碍再外扩一个平滑余量）

> 圆角半径做成常量导出，便于主题/LOD 调整。

### 4.6 ⑤ 端点锚定（浮动端点）

- 复用现有 `borderPoint`，但**按"路径首/末段方向"选择出入边**，而非固定用中心连线求交
- 效果：连线从节点"最自然的一侧"进出（对应 smart-edge 的 floating edges）

## 五、性能工程（对齐本项目既有调度纪律）

本项目硬纪律：**dirty-flag 单帧调度，空闲零 rAF / 零 timer**；**T8 大图降级**（>50K 走 Canvas，且 Canvas 模式下本就不渲染自由边）。

| # | 手段 | 说明 | 对齐点 |
|---|---|---|---|
| P1 | **按需寻路** | 通畅边零成本（4.2） | 直接减少每帧工作量 |
| P2 | **走廊裁剪** | 网格只覆盖边附近，非全画布 | 同上 |
| P3 | **TypedArray 网格** | `Uint8Array` + 扁平 open/closed 集 | 参照实测 20–24× 收益 |
| P4 | **布局版本缓存** | 路由结果按 `(sourceId, targetId, layoutVersion)` 缓存；**pan/zoom 不触发重算**（路由在世界坐标，与视口无关） | ✅ 关键：不与 pan/zoom 热路径耦合 |
| P5 | **LRU + 增量失效** | 移动某节点只失效「走廊与其相交」的边 | 拖拽重排时成本可控 |
| P6 | **帧预算守卫** | 单帧路由总耗时超预算（如 8ms）→ 余下边本帧走降级路径，下帧继续（渐进式） | 与「单帧调度」纪律一致，不引入常驻循环 |
| P7 | **低 LOD 跳过** | 复用现有 `lod === 'full'` 门控；缩小时不寻路 | 与树边命中区/chip 的既有策略一致 |
| P8 | （可选）**Web Worker** | 大图批量路由离主线程；先画降级路径再替换 | 仅在实测成为瓶颈时引入，避免过度设计 |

**不引入**：常驻 rAF 循环、布局求解器、力导向。

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| 网格分辨率导致贴障过近 | `nodePadding` 外扩 + 平滑余量；性质测试兜底 |
| 寻路抖动（节点微调导致路径跳变） | 拐点惩罚 + 缓存 + （必要时）路径相似度滞后 |
| 大图首批耗时 | 帧预算守卫 + 渐进路由 + 必要时 P8 Worker |
| 视觉回归（通畅边也变了） | `routeOnlyWhenBlocked` 保证通畅边走原路径，**逐点一致性测试**锁定 |
| 与动画帧插值（`animBoxes`）冲突 | 路由基于布局盒（世界坐标）；动画期间可沿用上一帧路由结果，动画结束重算 |

## 十、一句话结论

**用户判断正确——当前"恒定弓高贝塞尔"正是 GD 2009 论文点名批评的 ad-hoc 启发式。推荐采用「网格 A\* + 走廊裁剪 + 拉绳简化 + 圆角平滑」（react-flow-smart-edge 同款路线，有生产实测背书），配合按需寻路/布局版本缓存/帧预算守卫，在保持思维导图曲线审美、且大多数边零变化的前提下解决穿模。libavoid 的正交可见性图方案虽更"最优"，但直角折线与产品审美冲突且移植成本高，列为后续可选增强。**
