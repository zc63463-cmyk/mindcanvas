## 一、项目是什么

**dsh-synapse** 是 DeepSeek Harness（DSH）的可视化、非线性对话工作区插件：把同一工作区内的会话、追问、fork 分支组织成一张可拖拽、可缩放的「对话地图」，同时**保留 DSH 原生会话作为唯一事实来源**。

一句话：在原生聊天界面旁边加一个可切换的可视化工作台，让「谁从哪一轮分叉、哪条路还活着、当前焦点在哪」一眼可见。

**关键事实速览：**

| 维度 | 内容 |
|---|---|
| 形态 | DSH web profile 插件，仅注入 Web 组合补丁，复用宿主 Web Server，不启动第二个进程 |
| 数据边界 | 只读投影已提交的会话事件；不改 prompt/工具 schema/请求上下文，不影响 KV 缓存 |
| 存储 | 画布布局元数据独立存于 `$DSH_HOME/synapse/workspaces.json`（schema v4，自动迁移），删除不伤会话日志 |
| 技术栈 | Node.js ≥22.19，纯 JS（app.js / client.js / index.js / styles.css），极小代码面 |
| 节奏 | 2026-08-16 首发即 v0.3.0，10 天迭代到 v0.4.1（含一轮对抗性安全硬化） |

## 二、核心功能设计（8 项）

### 1. 会话地图 ↔ 原生对话一键切换
顶部「会话地图 / 对话」开关。进入画布，会话以卡片节点呈现；卡片上「在 DSH 中打开」随时回到原生界面。**可视化是增量能力，不要求用户放弃既有交互习惯。**

### 2. 真实分叉点连线（不制造第二套历史）
分支走 DSH 原生 session fork，画布按**真实分叉轮次**把节点连线——不是把会话列表平铺成无关卡片。这条纪律保证了地图的可信度：图上每条边都有据可查。

### 3. 持续投影 + 工具过程折叠
用户消息/助手回复投影到对应卡片；流式回复在卡片「详情」中持续更新；**工具调用与结果按 callId 配对，折叠进对应助手回复卡**——画布不被工具节点淹没，保持「思路级」颗粒度。

### 4. 双向会话同步
原生页与地图同步当前会话：任一侧切换焦点，另一侧跟随高亮。两个视图共享同一个「当前焦点」状态。

### 5. 画布交互全集
拖动画布、缩放（最高 4×）、移动卡片（位置自动保存）、展开/折叠后续对话子树、一键定位当前会话、卡片内平滑滚动。

### 6. 内容渐进披露
单条消息投影上限 8000 字符，超出截断并标注「详情查看全文」——卡片层保持摘要密度，全文按需下钻。

### 7. 失败回合可见（surface failed turns）
v0.4.1 加入：失败的回合在画布上有显式视觉状态，探索中的死路不再隐性。

### 8. 微配置面 + 安全边界显式化
仅 4 个配置键（dataFile / autoProjection / projectionWorkspaceTitle / trustedHosts），localhost 默认放行；对外安全扫描 L1-L4 通过、支持 pin commit 安装。

## 四、对本项目（mindcanvas）的启示

### 启示 1：架构方向被验证——「事实源 + 纯投影层」是对的
mindcanvas 的 `.mm.md` 纯文本事实源，与 dsh-synapse 的「DSH session log 为唯一事实来源、画布只是投影 + 独立布局元数据」完全同构。dsh-synapse 用 184 stars 证明了这个模式的用户价值：**布局/视图状态可删可重建，正文数据永不因视图层损坏而丢失**。mindcanvas 应坚持：未来任何视图状态（节点位置、折叠、相机）都进独立元数据层，不写回 `.mm.md` 语义内容。

### 启示 2：真实关系连线，杜绝「装饰性边」
关系图/图库的边必须全部来自 `.mm.md` 行内实体引用等真实数据，不允许手工摆放的「假边」。dsh-synapse 的可信度正来自「每条边 = 一次真实 fork」。这应写进 K 系验收标准。

### 启示 3：S 批产品壳可直接复用的 UX 细节清单
S1/S2 布局收口时逐条对照：
- 打开文档 → 定位到**最近编辑的节点**（非首节点），居中后 rAF 修正
- 大纲/画布/关系图视图切换，同文档不重置相机
- 滚动位置按文档隔离存储，切换文档不串位
- 画布背景色不能是纯白（光标可见性）
- 锚点式精确定位：点击大纲项滚到画布对应节点
- 高频视图状态写入做 microtask 合并

### 启示 4：B 线（LLM × 画布）的交互范式——折叠 + 渐进披露
dsh-synapse 的「工具调用按 callId 折叠进卡片 + 8000 字符截断 + 详情下钻」正是 mindcanvas B 线需要的：LLM 提议集、对账过程应折叠进对应节点卡，画布保持「思路级」密度；提议/校验失败要有显式视觉状态（对应它的 failed turns），不能静默。

### 启示 5：双向焦点同步是「多视图应用」的标配
F 自用周如果发现「在大纲里找了半天不知道画布在哪」，答案就是这套：全局唯一 focus 状态，所有视图跟随高亮。成本极低，体感极强。

### 启示 6：小切口 + 宿主复用 + 快速硬化 = 单人项目的正确发布姿势
一个单人项目 10 天内完成首发→硬ening→v0.4.1：复用宿主 server（不自建第二套）、极小配置面、把对抗性审查当质量门禁、失败可见。这与 mindcanvas「接口冻结 + 571 测试门禁」的纪律互补：**功能批次发布前，跑一轮对抗性审查作为门禁**。

### 启示 7（风险对照）：多实例写冲突要提前想
dsh-synapse 踩过的坑：两个实例共享同一数据文件会互相覆盖。mindcanvas PWA/local-first 将来若出现多标签页/多设备，`.mm.md` 与元数据的并发写需要类似「写锁 + 外部修改警告」机制，而不是乐观假设单实例。

## 五、适用性判断

| 项 | 判断 |
|---|---|
| 直接复用？ | ❌ 不适用——它是 DSH 会话可视化，不是思维导图 |
| 抄架构？ | ✅ 事实源/投影分离、独立元数据存储、只读投影纪律 |
| 抄交互？ | ✅ 上表 UX 细节清单直接进 S 批验收 |
| 抄流程？ | ✅ 对抗性审查门禁、事件写入合并、失败显式化 |
| 参考 WBS | 若 F 周暴露多视图同步摩擦，dsh-synapse 的双向同步实现可作为对照实现读源码（app.js/client.js 共 ~3 文件，可读性高） |

---

**结论**：dsh-synapse 与 mindcanvas 不是竞品，而是同一个架构信念（画布 = 真实数据的投影，不是第二套数据）在 AI 对话领域的成功落地。它对本项目最大的价值不是功能移植，而是三件可立即执行的事：① S 批验收加入其 UX 细节清单；② B 线采纳「折叠 + 渐进披露 + 失败显式化」的画布-LLM 交互范式；③ 发布流程引入对抗性审查门禁。
